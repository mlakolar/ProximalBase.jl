AtomIterate: grouped storage implementation

For the supported entry and group operations, begin with the user guide; for group trial points and KKT screens see coordinate oracles. This page describes invariants needed when changing src/atom_iterate.jl. The iterate-family contract is authoritative.

Two index spaces and one active set

AtomIterate{T,G} <: AbstractVector{T} exposes ordinary entry indexing x[j], but its optimization coordinates are groups. The groups must partition 1:length(x) into nonempty, disjoint sets. The implementation validates the partition when an iterate is constructed and creates a group_of[j] reverse map so that an entry write can find its group in constant time.

The main private data are:

FieldRole
storageDense entry buffer, with zeros in inactive groups
groupsImmutable-in-use partition, retained as ranges or owned vectors
group_ofEntry ID to group ID
active, position, nactivePacked active-group list and reverse positions
layout_cacheOne previously verified equal group layout, used for a fast equality hit

An active group may contain only zeros. A nonzero entry write activates its group; a zero write does not deactivate it. dropzeros! inspects active groups and removes all-zero groups, possibly swapping a surviving group into a removed slot. Never store solver history keyed by active slot across compaction without remapping. Raw writes to storage that bypass activation can leave an inconsistent iterate: do not use them in solver code.

Group layout and read-only handles

atom(x,k) is a live view of group entries through x, so scalar writes still activate the group. atomindices(x,k) gives a read-only index collection. Stored ranges are returned as ranges; stored vector groups are exposed through the private _GroupIndices wrapper, which rejects writes and preserves underlying alias identity. A caller must not mutate groups or reach the original group arrays through wrapper fields.

samegroups(a,b) is public but not exported. For two iterates, or an iterate and a group penalty, it compares the ordered groups and the indices within each group. Equal ranges and vectors agree by value, but reordered groups or reordered members do not.

The layout_cache stores at most one verified equal layout. Repeated comparison against that exact layout is constant time; comparisons against a different layout may inspect all indices. A positive comparison of two iterates can benefit from already shared cache identities. This cache does not change the mathematical groups and must not be used as a reason to mutate an otherwise shared layout. Copies retain their layout records; state copying does not overwrite the destination's cache.

Oracle boundaries and failure behavior

The five-argument prox_coordinate!(x,f,k,u,γ) is the supported block trial-point interface. It validates group compatibility before writing the trial's result. Writing a tentative group into private storage first and then calling the four-argument method is not equivalent: an inactive group may contain nonzero entries while remaining absent from the active set. The same separation applies to KKT screens, which are function methods, not part of the base storage type.

Ordinary array writes and a same-kind iterate state copy have distinct preflight and activation semantics. Test both routes, including aliasing through atom(x,k) and an index permutation. External oracles must maintain consistency even when they write only a subset of groups.

Testing and performance

Relevant tests include test/atom_iterate.jl, test/iterate_queries.jl, test/iterate_writes.jl, test/active_handle.jl, test/symmetric_groups.jl, and the family acceptance matrix. Benchmark Float32 and Float64 vector hot paths, both contiguous and noncontiguous groups, warm and cold layout comparisons. Do not infer an O(1) equality comparison merely because a cache exists.
