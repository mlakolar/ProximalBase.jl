SymmetricSparseIterate in 0.6: migration and acceptance

Draft for maintainer review — proposed 0.6 behavior, not a description of an installed release. This guide explains how real callers move to the contract and how a future implementer proves conformance. It links to the contract's requirement IDs and restates none of the rules. Nothing in it is implemented, except the three-factor product A * X * B of FD-16 (#419) for homogeneous Float32 and Float64; the remaining owner changes are future work. Every julia block that uses matrixview, activevalues or an owner that is not an AbstractMatrix is a future example; none is a doctest.

Amendment and extensions from the iterate-family contract (#400), signed off on 2026-11-01. The iterate-family contract changes one expectation here. The text below is left as written; where it differs from the amendment, the amendment applies.

  • FD-9: in T13, mul!(y, matrixview(X), [Inf, 1, 0]) gives [0, 1, 0] before and after dropzeros!(X), instead of "the recommended default throws in both" (decision 13 and PERF-6's default). PERF-6's requirement is amended to the same contributing terms (FD-9 option (i)), because compaction can reorder finite contributions; T13's simple zero fixture is unaffected.
  • Consistent extensions, with no change here: the read-only handle of ACT-3 is shared by the family, and a handle taken before a state copy or a CPY-4 import is not reused after it (FD-7); oracle destinations follow FD-4; and the owner's *(A::Symmetric, X::SymmetricSparseIterate, B::Symmetric) follows FD-16 (#419, decided 2026-11-06: the direct sum over the nonzero entries of X, an off-diagonal coefficient counting for both of its entries) for Float32 and Float64, implemented against the stored fields nzval, nzval2ind, nnz and p and rechecked when #737 changes the storage; other element types keep 0.5.x's method; and in T10, a state copy converts only the source's active values and one that throws leaves the destination unchanged (#416, FW-4).

2. Migration

2.1 X[k] cannot be migrated by search-and-replace

At 0.5.x X[k] is the matrix entry at linear index k (since #22). In 0.4 and earlier it was lower-triangle coordinate k. Callers that were written for the old meaning may still read it that way. Identify the intent first (contract IDX):

what k is at that site0.6 form
a coordinate ID, from 1:ncoordinates(x) or tril_indexcoordinates(x)[k] (hoist cx = coordinates(x) out of a loop)
a matrix linear index, from 1:p² or (c-1)p + rmatrixview(x)[k]
a slot in activecoordinates(x)activecoordinates(x)[a] for the ID, activevalues(x)[a] for the value
r, c already knownx[r, c] (unchanged)

Verified at the audited commit for p = 3: coordinates(X)[4] is the (2,2) variable and X[4] is the (1,2) entry.

X[k] itself should throw an ArgumentError that names both replacements (OWN-3), so a missed site fails loudly with its fix in the message.

2.2 The five patterns

(a) A matrix linear index against a CD coordinate. ProximalSolvers already reads coordinates through the view and is unchanged:

# src/cd/kron.jl:104–118, 0.5.x and 0.6 alike
cx  = coordinates(x)
old = cx[k]                      # coordinate k, not matrix entry k
...
cx[k] = new

(b) Updating all independent variables, against sweeping the active set.

# 0.5.x: looks like "scale every entry"; quadruples off-diagonal entries
for j in 1:p, i in 1:p
    x[i, j] *= 2
end

# 0.6: every independent variable, once (O(q); an absent coordinate stays absent)
θ = coordinates(x)
θ .*= 2

# 0.6: only the working set (O(s))
v = activevalues(x)
v .*= 2

# 0.6: an active-set sweep with a solver step (ACT-3, ACT-5)
act = activecoordinates(x)
for a in eachindex(act)
    coordinate_step!(model, g, x, act[a])    # never changes `act`
end

src/cd/solver.jl:318 (_activepass!) is already this loop; :280 (_fullpass!) loops 1:ncoordinates(x). Neither changes.

(c) Passing the iterate to a matrix-reading algorithm.

# 0.5.x: the iterate is an AbstractMatrix
get_confusion_matrix(Δ, hΔ)          # Δ::AbstractMatrix, hΔ::AbstractMatrix (src/evaluation.jl:25)
eigvals(Symmetric(x))

# 0.6
get_confusion_matrix(Δ, matrixview(hΔ))
eigvals(Symmetric(matrixview(x)))    # generic read, O(p²) assembly
mul!(y, matrixview(x), v)            # O(p + s), PERF-6

The signature get_confusion_matrix(::AbstractMatrix{T}, ::AbstractMatrix{T}) is a verified break for an owner argument. Whether any caller passes one I could not tell from the tree.

(d) A dense writable workspace.

# 0.5.x: loops over private storage
fill!(D, 0)
for k = 1:nnz(Δ)
    r, c = tril_cartesian(Δ.p, Δ.nzval2ind[k])
    D[r, c] = D[c, r] = Δ.nzval[k]
end

# 0.6
copyto!(D, matrixview(Δ))        # into a buffer you own
D = Matrix(x)                    # a fresh dense snapshot
W = similar(matrixview(x))       # a Matrix{T}, MAT-4

This is CovarianceSelection src/directDifference.jl:125–131 (_densify!).

(e) Copying or allocating another solver iterate.

x2 = copy(x)                      # active zeros and order preserved (CPY-1)
x3 = similar(x)                   # empty (CPY-2)
copyto!(x3, x)                    # state copy (CPY-3), replaces x3's working set
copyto!(x3, M)                    # checked import of a symmetric matrix (CPY-4), replaces

Base.copy! is not part of the owner's interface; ProximalSolvers' _copy!(y, x) = copy!(y, x) (src/blocks.jl:39) must call copyto! for owners.

The mathematics of either model does not change; the dimension reads do (above). What can break them is elsewhere: the x they are given must be an owner that supports coordinates, activecoordinates and size, which the contract keeps. They must read the dimension as size(x, 1), not x.p.

4. Performance protocol (a future measurement, not a result)

No timing was run for this document. The protocol:

  • Environment to record: Julia version and JULIA_NUM_THREADS, CPU model, OS, ProximalBase commit, --check-bounds setting. The benchmark harness is benchmark/ (see its README); BenchmarkTools is not installed in the default environment, so use the harness's own timing.
  • Warm-up: call each case once untimed, then GC.gc(); allocation counts come from @allocated on the second call; time the minimum of at least 30 repetitions of a batch.
  • Timed first activation. Warm up on a different coordinate or fixture. Every timed first activation must begin with an absent coordinate; otherwise repeated samples measure the already-active path. Restore the state (dropzeros! of a stored zero, or a fresh owner) outside the timed region.
  • A real coordinate sweep. Include a warmed-up active sweep that calls prox_coordinate! with a built-in separable f, not only a trivial assignment, and a KronModel sweep for the cached case.
  • Pre-refactor baseline. Report the 0.5.x SymmetricSparseIterate (abaceda25) beside the new owner for every case above that both support, in the same session. The CSC and dense baselines answer the matrix-product question; only the pre-refactor owner answers whether existing coordinate descent became slower.
  • Fixed s = 100, p ∈ {500, 1000, 2000, 4000}. For each, record: construction; X[i,j] read and write (cycling through a precomputed list of active and absent positions); first activation of an absent coordinate; an active sweep for k in activecoordinates(X) with a trivial update; mul!(y, matrixview(X), v); Matrix(X).
  • Fixed p = 1000, s ∈ {10², 10³, 10⁴, 10⁵}. Record the same, with the sweep and mul! as the cases of interest.
  • Targets (future, from PERF):

5. Review gate

  1. Which interface do I index? X[i,j] for a matrix position; coordinates(X)[k] for a variable by ID; activecoordinates(X)[a] for an ID by slot; matrixview(X)[i] for a matrix linear index (§2.1, IDX-1..4).
  2. Does a write change the working set? A nonzero write to an absent coordinate activates it; a zero write to an absent one does not; a write to an active one never removes it; only dropzeros! removes (CRD-3, ACT-5, ACT-6). T03.
  3. Where does the factor of two enter? In the objective, never in storage: multiplicity mₖ multiplies the penalty and the quadratic along Eₖ; a coordinate model returns joint-direction derivative and curvature; the entrywise step is mₖ/a; the KKT residual is entry-normalized (contract §2.8). T05, T07, T14.
  4. What is actually checked? Exact pairwise symmetry of caller data, on the source values, before conversion; a coordinate call checks its pair, a bulk write checks everything it will write before writing; the whole model is certified only by check_symmetric_parameters on the caller's original penalty (VAL-1..8, T04, T06, T17). kkt_violation screens a coordinate at zero; it certifies no solution (T16).
  5. Can a dense scan or allocation occur? The cases in PERF-1..7 do not; generic matrix operations on the view may (PERF-8) and the list of those promised sparse-fast is closed.

Does every important guarantee have an acceptance case? Yes, by the coverage line in §3, with two exceptions that are deliberate: PERF-8 (a non-promise) and the "unsupported, tracked elsewhere" families of ORC (#336, #342), which are tested by their own issues. Does the design remove the need for a catalog of forbidden Julia mutators? It removes the catalog for the owner (nothing generic reaches it, OWN-1/OWN-3) and for the view (read-only, MAT-2). It does not and cannot protect an explicit double loop over (i, j) on X[i,j] that reads and writes a mirrored variable, as the contract says.
