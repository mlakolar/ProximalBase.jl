SymmetricSparseIterate in ProximalBase 0.6: the contract

Draft for maintainer review — proposed 0.6 behavior, not a description of an installed release. Phase 1 of the owner is implemented on the development branch: the owner is not an array, with coordinates, matrixview, the active-coordinate handles, pair indexing, state copies and checked imports, owner-to-owner equality and hash, the one throwing axes, the proximal, gradient and Hessian oracles and the wrappers that the owner supports, and the products and reductions with strong zeros, including the three-factor product A * X * B of FD-16 (#419) for homogeneous Float32 and Float64. The other phases of #391, the migration of the solvers that use the owner (#527) and the release remain. This file is the only normative document of the pair; the companion migration and acceptance guide links back to it and restates none of its rules.

Amendment and extensions from the iterate-family contract (#400), signed off on 2026-11-01. The iterate-family contract changes one rule of this file and extends several others without changing them. The text of this file is left as #388 signed it off; where it differs from the amendment below, the amendment applies.

  • FD-9: a zero coefficient of the owner contributes nothing to a product with one owner operand, even against Inf or NaN. Replaces decision 13 and PERF-6's recommended default (an ArgumentError after an O(p) scan). FD-9 also amends PERF-6's requirement (option (i), chosen 2026-11-01): dropzeros! keeps the same contributing terms, and their finite evaluation follows FN-4 and A1, because compaction can reorder finite contributions and change a finite overflow.
  • Consistent extensions, with no change to the rules here:
    • ACT-3's read-only handle type is shared by the whole family, and the lifetime of the ACT-3 and ACT-4 handles also ends at a whole-state replacement (CPY-3's state copy or CPY-4's import), which can reorder the slots without changing nactive (FD-7);
    • oracle destinations follow FD-4, consistent with ORC-3 and ORC-6;
    • the owner's *(A::Symmetric, X::SymmetricSparseIterate, B::Symmetric) follows FD-16 (#419, decided 2026-11-06: the direct sum over the nonzero entries of X, an off-diagonal coefficient counting for both of its entries) for Float32 and Float64, implemented against the stored fields nzval, nzval2ind, nnz and p and rechecked when #737 changes the storage; other element types keep 0.5.x's method;
    • CPY-3's state copy converts only the source's active values, and one that throws leaves X unchanged (#416, FW-4). This strengthens, for CPY-3 alone, §2.10's statement that a throwing conversion is not promised to leave X untouched.
  • CPY-4 stands as written: the family contract keeps the owner's checked replace (FD-3).

Audited commits. ProximalBase abaceda25442bf6cc61601c8c1d3b2a16e1a3492 (master, 2026-11-01; Project.toml says 0.5.4). Links below point at that commit. ProximalSolvers 3893fb9 (master), read as evidence only. The other consumers and what was not audited are listed in the companion guide.

How to read it. Part 1 is for a Julia user and needs no implementation knowledge. Part 2 is for a package or solver author: requirements carry stable IDs, must marks a public guarantee, and recommended marks an implementation idea that a conforming implementation may replace. Part 3 lists the choices the maintainer must sign off. Part 4 is informative evidence.

Part 1. The idea in one page

A real symmetric matrix X of size p × p has p(p+1)/2 independent numbers: the lower triangle. X[2, 1] and X[1, 2] are one variable, not two. An optimization solver wants to see those p(p+1)/2 variables. A matrix routine wants to see a p × p matrix. If one object offers both faces as a writable AbstractMatrix, an innocent loop can touch one variable twice:

for j in 1:p, i in 1:p
    X[i, j] *= 2          # 0.5.x: X[2,1] is doubled twice, so it is quadrupled
end

(Run at the audited commit: an off-diagonal 1.0 becomes 4.0.) No list of patched Base functions can make every such loop right. So SymmetricSparseIterate in 0.6 is not a matrix and not a vector. It owns the variables and hands out two views of that one state, plus scalar access by two indices:

X = SymmetricSparseIterate(Float64, 3)
θ = coordinates(X)                   # live and writable; six independent variables
A = matrixview(X)                    # live and read-only; a 3 × 3 matrix

X[2, 1] = 3.0
@assert A[1, 2] == A[2, 1] == 3.0
@assert nactive(X) == 1
@assert sum(abs, θ) == 3.0
@assert NormL1(1.0)(X) == 6.0       # the matrix penalty counts both positions

B = Matrix(X)                        # an independent dense copy
θ[tril_index(3, 2, 1)] = 5.0
@assert A[1, 2] == 5.0 && B[1, 2] == 3.0

Why each assertion holds:

  • X[2, 1] = 3.0 writes one variable. Reading A[1, 2] or A[2, 1] sees it, because A is a view of X, not a copy.
  • nactive(X) == 1: the working set holds one coordinate (one variable), not two matrix positions. A zero is not stored; a nonzero write activates its coordinate.
  • sum(abs, θ) == 3.0: θ is an ordinary vector of the six variables, so an ordinary vector function sees 3.0 once.
  • NormL1(1.0)(X) == 6.0: the penalty is a function of the matrix, whose two positions both hold 3.0. Its argument is the owner, so it uses the matrix meaning. (NormL1(1.0)(θ) is 3.0: a vector argument gets the vector meaning. The two are different functions on purpose.)
  • Matrix(X) copies. After θ[2] = 5.0 the copy B still says 3.0 while the live view A says 5.0. (tril_index(3, 2, 1) is 2.)

Three different indices

indexrangenamesdurable?
matrix linear index i1:p²the column-major position of matrixview(X)[i]yes: a mathematical location
coordinate ID k1:q, q = p(p+1)/2the variable coordinates(X)[k], k = tril_index(p, r, c) with r ≥ cyes: a mathematical location
active slot a1:s, s = nactive(X)the a-th entry of the current activecoordinates(X)no: a storage position

Only the first two describe where something is. A slot must never be kept as an ID, because dropzeros! moves coordinates between slots. Confusing the first two changes the answer. For p = 3 the lower triangle in column-major order is (1,1), (2,1), (3,1), (2,2), (3,2), (3,3), so

coordinates(X)[4]    # the variable at (2, 2)
matrixview(X)[4]     # the matrix entry at (1, 2): linear index 4 is row 1, column 2

(Both checked at the audited commit, where X[4] is the matrix reading.)

Where the factor of two lives

In a matrix objective an off-diagonal variable stands for two positions. That factor of two belongs to the objective (the Frobenius inner product), not to the storage. A vector of coordinates has no factor of two, so coordinates(X) is correct for anything linear: you may double every coordinate and double the matrix. It is wrong for matrix norms: norm(θ) is 3.0 for the example, norm(X) is 3√2. A coordinate solver therefore never rescales storage; it asks the oracles, which know the multiplicity, and it measures curvature along the matrix direction (§2.8).

What changes for you

Iterate with coordinates(X) or activecoordinates(X). Pass the owner to functions that mean the matrix. Pass matrixview(X) to code that reads a matrix, and Matrix(X) to code that needs a dense writable one. There is no X[k], no length(X), and no broadcasting on the owner. The companion guide walks through real callers.

Part 2. Requirements

Notation. p is the dimension, q = p(p+1)/2, s = nactive(X). X is an owner, θ = coordinates(X), A = matrixview(X). T = eltype(X) is a real fixed-width type. m_k is the multiplicity of coordinate k: 1 on the diagonal, 2 off it.

2.1 The owner

IDRequirement
OWN-1SymmetricSparseIterate{T} must keep its name and its constructors SymmetricSparseIterate(T, p) and SymmetricSparseIterate(p) (Float64). It must not subtype AbstractArray, AbstractMatrix or AbstractVector.
OWN-2X[i, j] and X[i, j] = v must be supported for integers 1 ≤ i, j ≤ p, from either triangle, bounds-checked, naming one variable. Out of range must throw BoundsError.
OWN-3X[k], X[k] = v, length(X), eachindex, axes, iteration, firstindex/lastindex, map, reduce and broadcasting on the owner must not return values. X[k] should throw an ArgumentError that names coordinates(X)[k] and matrixview(X)[k]; the others may be a MethodError.
OWN-4size(X) must be (p, p) and size(X, d) must be p for d ∈ {1, 2}. eltype(X) must be T. ncoordinates(X) must be q.
OWN-5Complex T must throw an ArgumentError at construction, as today.

Recommended default for length: undefined. Reason: the two natural answers (p² and q) are both "right" for some caller, and #22 shows what a wrong one costs. Consequence for a caller: length(X) is a MethodError; use ncoordinates(X) (q), size(X, 1) (p) or length(A) (p²). Recommended default for size: keep (p, p). Reason: the dimension is unambiguous, and ProximalSolvers checks it as the shape of a model (initialize! of KronModel, src/cd/kron.jl:65). Consequence: size does not make the owner an array; no generic array code applies to it.

With no AbstractArray supertype, Base and LinearAlgebra have no generic method that writes the owner. The only writes are the methods named in this document. That is what removes the need for a catalog of forbidden mutators (compare the SymmetricSparseIterate override list in src/sparse_iterate.jl and the 1,130 lines of tests that guarded it).

What this does not make safe. An explicit double loop over (i, j) that reads and writes X[i, j] still updates a mirrored variable twice. The owner cannot prevent that and does not claim to. What it removes is the implicit double loop that a Base function runs on your behalf.

2.2 Index spaces

IDRequirement
IDX-1The coordinate ID of the lower-triangle position (r, c), r ≥ c, must be tril_index(p, r, c); IDs must follow column-major order of the lower triangle, as today. tril_cartesian(p, k) must invert it.
IDX-2X[i, j] with i < j must denote the variable of (j, i).
IDX-3prox_entry(f, v, i, γ) takes a matrix linear index i = (c − 1)p + r (it indexes weights and bounds, which are matrices). This is the one place an oracle takes a matrix linear index; every coordinate operation takes an ID k. Docstrings must say which.
IDX-4An integer passed to a coordinate API (coordinates(X)[k], isactive, activate!, prox_coordinate!, kkt_violation) is always interpreted as an ID. A caller holding a slot a writes activecoordinates(X)[a]. When a slot and a valid ID are the same Int the implementation cannot tell the intent, and no new index type is introduced to do so.

2.3 The coordinate view

IDRequirement
CRD-1coordinates(X) must return an AbstractVector{T} of length q, live (reads and writes reach X), writable, O(1) to construct, with no copy of data.
CRD-2Reading an absent coordinate must return zero(T) and must not activate it.
CRD-3A write first converts v to T; activation is decided from the converted stored value. If iszero(convert(T, v)) and the coordinate is absent, it must not be activated: writing 1e-100 to an absent Float32 coordinate leaves it absent (the audited code already does this). A nonzero converted value (NaN included) must activate it. Writing to an active coordinate must store the converted value, including zero, and must not deactivate it. Symmetry of a mirrored pair is a different question and is decided on the source values before conversion (VAL-2).
CRD-4θ must be an ordinary vector: sum(abs, θ), norm(θ), θ .= …, fill!(θ, 0), rmul!(θ, 2) mean what they mean for any vector of q numbers. In particular a full traversal of θ visits q coordinates, not s. Linear operations on θ are therefore correct for the matrix (doubling every coordinate doubles the matrix); norms and inner products are not matrix norms (§2.8).
CRD-5Broadcasting θ .= g.(…) must obey CRD-3 per coordinate. It must give the same result as the explicit loop for k in 1:q; θ[k] = g(…); end.

2.4 The matrix view

IDRequirement
MAT-1matrixview(X) must return an AbstractMatrix{T} of size (p, p) with ordinary matrix indexing (linear and Cartesian) and both triangles, O(1) to construct, with no copy of data, live.
MAT-2A must be read-only: no mutation through A or any wrapper derived from it (view, reshape, transpose, Symmetric(A), vec). Recommended: define no setindex! for the view, so the derived wrappers inherit the refusal. What is required is that the write is rejected and X is unchanged; the exception type is not specified, and no override should be written only to produce a particular exception for an exotic wrapper.
MAT-3Read-only is not a snapshot and not an immutable owner: A must reflect later writes to X, and X stays mutable.
MAT-4A generic allocating operation (A .+ 1, A * v, similar(A), copy(A), collect(A)) must give an ordinary writable dense result and must not give a route to X. similar(A) must be a Matrix{T}.
MAT-5Base.dataids(A) should be Base.dataids of the owner's storage so that Base.mightalias and Base.unalias see that A and X share memory.
MAT-6A must satisfy the AbstractArray interface for reading: A[i] == A[CartesianIndices(A)[i]], length(A) == p², iteration yields p² entries. (This is #22's rule, kept for the view and removed from the owner.)

Matrix(X) (and Array(X)) must return a fresh dense symmetric Matrix{T}, O(p² + s), independent of X.

2.5 Copies and whole-value writes

Three operations that look alike are different: a state copy (the working set travels), a checked import (a matrix becomes the value), and a dense snapshot (Matrix(X)).

IDOperationRequirement
CPY-1copy(X)must create independent solver state: same p, same values, same set of active coordinates, active zeros preserved, and the activation order of X. O(q).
CPY-2similar(X), similar(X, S)must return an empty owner (no active coordinates, all values zero) of the same p, with element type T or S. O(q) memory.
CPY-3copyto!(X, Y::SymmetricSparseIterate)must make X a state copy of Y (CPY-1), discarding the previous working set of X. Different p must throw DimensionMismatch before writing. copyto!(X, X) must be a no-op. (Consistent extension: #416 and FW-4, iterate-family contract: only active values are converted, and a copy that throws leaves X unchanged.)
CPY-4copyto!(X, M::AbstractMatrix) and SymmetricSparseIterate(M)must be a checked import (§2.10): M must be square of size (p, p) and exactly symmetric. Default: replace. After the call X equals the converted M, the working set is exactly the coordinates whose converted stored value is nonzero, in increasing ID order (CRD-3 rule), and the previous working set (explicit zeros included) is gone. Symmetry is checked on the source values before conversion (VAL-2). O(q) time (a dense source is read once).
CPY-5Matrix(X)dense, independent, writable snapshot (§2.4).
CPY-6an aliasing sourceA source that shares memory with X (matrixview(X) or a derived view) must be rejected with an ArgumentError before writing.

Default for CPY-4: replace. Reason: the result then depends only on the argument, not on what X held before, so a warm start from a dense matrix has the support of that matrix. Consequence for a caller: a solver that wants to keep its working set while loading values writes θ .= … (CRD-5) or loops over activecoordinates; it does not import. An import never leaves an active coordinate that the new matrix does not make nonzero.

2.6 Stored coordinates and the active set

Three counts must not be confused:

quantitymeaninghow to get it
stored coordinatesthe working set, explicit zeros includednactive(X) (= s)
mathematically nonzero coordinatesthose with value ≠ 0count(!iszero, activevalues(X)) (O(s))
nonzero full-matrix positionsboth trianglescount(!iszero, A) (O(p²), generic)
IDRequirement
ACT-1ncoordinates, nactive, activecoordinates, isactive, activate! and dropzeros! must be kept with today's meanings, on IDs. isactive(X, k) is O(1) and must not allocate.
ACT-2nnz(X) is not retained. It must be undefined for the owner. nactive(X) replaces it. A matrix-view nnz is not added: no audited caller needs one. SparseArrays.sparse(A) is the way to ask a matrix question (recommended: O(p + s)).
ACT-3activecoordinates(X) must return a read-only AbstractVector{Int} of the IDs of the active coordinates in slot order, of length s at the call. It is a handle, not a snapshot: its entries are valid IDs, in unchanged slots, for as long as the active set is unchanged. It must be reacquired after any activation or compaction. Use of a stale handle after dropzeros! is not specified (the slots may have moved) but must not be memory-unsafe. (Consistent extensions: FD-7, iterate-family contract: one handle type for the family, and a whole-state replacement also ends the handle.)
ACT-4activevalues(X) (new name) must return a writable AbstractVector{T} of length s whose entry a is the value of coordinate activecoordinates(X)[a]. Writing zero through it keeps the coordinate active. Same lifetime as ACT-3. It is the supported replacement for reading and writing the first nnz stored values by slot. (Consistent extension: FD-7, iterate-family contract.)
ACT-5Writing a value (CRD-3, X[i,j] = v, activevalues, prox_coordinate!) must never remove an active coordinate. Only dropzeros! removes a single coordinate, and only one whose value is zero. The one exception is whole-state replacement: copyto!(X, Y) and copyto!(X, M) (CPY-3, CPY-4) discard the previous working set by design, and copy and state copies preserve active zeros. A sweep over activecoordinates(X) that only updates already active coordinates must leave activecoordinates(X) unchanged, whatever values it writes.
ACT-6activate!(X, k) is the explicit-zero operation: it makes k active at value zero if it is absent and changes nothing otherwise. After X[3,1] = 0.0 (absent) nactive is unchanged; after activate!(X, tril_index(3,3,1)) it is one larger.
ACT-7dropzeros!(X) must keep every value, every owner/view relation and every ID unchanged. It may reorder slots (today: the last active coordinate moves into each freed slot). It must run in O(s) and not allocate.
ACT-8What survives compaction: X, θ and A keep denoting the same variables and values; coordinate IDs do not change; slot order and any handle from ACT-3/ACT-4 do not.

Recommended extra accessor: none. A caller that needs (k, value) pairs zips activecoordinates(X) and activevalues(X).

2.7 Cost of compaction and handles: why a handle and not a snapshot

A snapshot of the active IDs would cost O(s) per sweep and an allocation, which the active-set solvers avoid. ProximalSolvers' momentum history already keys by slot and restarts when the count changes, because dropzeros! reorders (src/cd/solver.jl:190–200). ACT-3 states that rule as part of the contract instead of leaving it a comment in one solver.

2.8 The mathematics, independent of storage

The object. The variable is a real symmetric matrix Z with the Frobenius inner product ⟨U, V⟩ = Σᵢⱼ UᵢⱼVᵢⱼ. In coordinates

‖Z‖²_F = Σₖ mₖ θₖ²,      mₖ = 1 (diagonal), 2 (off-diagonal).

Coordinates are not rescaled by √2: X[r, c] is the matrix entry. A function of coordinates(X) that is an ordinary vector function stays one (CRD-4). The orthonormal-coordinate alternative √mₖ θₖ would make vector functions right but would make X[2,1] ≠ coordinates(X)[2], so every stored number would need a conversion at each read.

A direction. Moving coordinate k by t moves Z by t Eₖ, with Eₖ = e_r e_cᵀ + e_c e_rᵀ (Eₖ = e_r e_rᵀ on the diagonal), and ‖Eₖ‖²_F = mₖ.

Smooth example. Let f(Z) = ½‖Z − B‖²_F with symmetric B, B[2,1] = 3, p = 2, and Z[2,1] = t, the rest zero. Then f along the coordinate is (t − 3)² + const.

  • The matrix gradient projected on the symmetric subspace is G = Z − B, with G[2,1] = t − 3.
  • The raw directional derivative along coordinate k is ⟨G, Eₖ⟩ = mₖ G[2,1] = 2(t − 3).
  • The curvature along the joint direction is ⟨Eₖ, H Eₖ⟩ = 2 (here H = I).
  • For an ambient (not symmetric) gradient Ĝ the same directional derivative is Ĝ[2,1] + Ĝ[1,2]. If Ĝ[2,1] = 2 and Ĝ[1,2] = 0 it is 2, the same as for its symmetric part (1 in each position, times m = 2). A solver that read Ĝ[2,1] = 2 as "the entry" and then multiplied by m would get 4.

Convention for a coordinate model (the one the audited solvers already follow, coordinate_derivatives and _symcurvature in src/cd/kron.jl:97–101): it returns the derivative and curvature along Eₖ, already combined over the two positions. A solver must not multiply either of them by 2 again.

Proximal example, with the check you can do by hand. Minimize ½‖Z − B‖²_F + λ Σᵢⱼ |Zᵢⱼ| with symmetric B, B[r,c] = 3, λ = 0.5. On the coordinate the objective is (t − 3)² + 2λ|t|; the doubled quadratic and the doubled penalty cancel and the minimizer is 3 − λ = 2.5, not 2.0. At the audited commit, prox! into an owner, prox_entry(NormL1(0.5), 3.0, 2, 1.0), prox_coordinate!(X, NormL1(0.5), k, 3.0, 1.0) and a joint-direction coordinate step all give 2.5.

The step that the entrywise prox sees depends on how the curvature is normalized. Let a be the curvature along Eₖ and a_u = a / mₖ the curvature along the unit-Frobenius direction Eₖ/√mₖ. The scalar problem d(t − θ) + (a/2)(t − θ)² + mₖ gᵢ(t) is minimized at

θ⁺ = prox_{(mₖ/a) gᵢ}( θ − d/a ),     entrywise step  mₖ/a = 1/a_u.

So the step handed to prox_entry, and the γ of the four-argument prox_coordinate!, is the reciprocal of the curvature measured along a unit-Frobenius direction. For the example a = 2, mₖ = 2: step 1, giving 2.5. Using step 1/a = 0.5 (curvature normalized but the penalty not doubled) gives 2.75; using step 2 (penalty doubled, curvature entry-normalized as 1) gives 2.0. Both are wrong, silently.

Screening is not stationarity. kkt_violation answers one question: does coordinate k, at zero, violate optimality, so that it should enter the working set? Its maximum over all coordinates does not certify a solution. Counterexample: at a coordinate with value x > 0, projected matrix gradient G = +1 and λw = 1, the screen is |1| − 1 = 0, yet the entry-normalized derivative of the objective is G + λw = +2 and the point is not stationary. The public screening API is kept. The residual of a returned solution is a separate quantity, entry-normalized like the screen:

r_k = max(|G_k| − λ w_k, 0)        if x_k = 0
r_k = |G_k + λ w_k sign(x_k)|      if x_k ≠ 0          (weighted L1 penalty)

and the Frobenius-weighted total is Σₖ mₖ r_k². These are different numbers: for one off-diagonal pair with r_k = 2, maximum(r) = 2, the Frobenius residual √(Σ mₖ r_k²) is 2√2, and its square is 8. A solver states which one it reports; the stopping policy is the solver's. Here G_k is G[r, c] for the lower-triangle coordinate ID k (k is not a matrix linear index).

Public screening API. kkt_violation(f, g, X, k) takes the matrix gradient g (its symmetric part is used) and returns the residual in the entry normalization: |G[r,c]| − λ w[r,c] for NormL1. It divides out mₖ, because both the derivative and the penalty carry it. A solver that holds the coordinate derivative dₖ must pass dₖ / mₖ (or the matrix gradient), never mₖ dₖ. Optimality of the whole problem in the Frobenius norm weights residuals by mₖ: Σₖ mₖ rₖ².

2.9 The oracles

Which argument decides the space. A value or gradient oracle follows its point argument; a proximal oracle follows its destination. An owner (as point or destination) means real symmetric matrices with the Frobenius inner product and both positions counted. A plain matrix means ordinary matrices. A coordinate vector (θ) means ordinary vectors. A function that accepts AbstractMatrix is not thereby a symmetric-constrained proximal operator: only the rows below, for the families they name, are promised.

Supported families. Separable penalties and losses with symmetric per-entry parameters; the spectral and LogDetLoss/KronQuadratic families where today's code computes them on a symmetric matrix. A caller that needs one of these gets an error, not a guess.

2.10 Validation and numerical boundaries

Three operations, not one.

  1. Storing a matrix (import, constructor, copyto! from a matrix): the value must be exactly symmetric. Copying an asymmetric matrix is an error; it is not a projection.
  2. Declaring model parameters (weights, bounds, labels, centers, per-entry steps, normals, c of a linear term): mirrored entries must agree exactly. There is no silent averaging and no preferred triangle (#142, amendment of 2026-10-30). Symmetric(W, :L) is the caller's explicit choice of a triangle; it is not evidence that the original array was symmetric.
  3. Projecting an ambient quantity inside an oracle. The gradient g given to kkt_violation, and the gradient an oracle writes, are projected onto the symmetric subspace. So is the argument V of a proximal map under a scalar Frobenius step γ: for symmetric Z, ‖Z − V‖²_F = ‖Z − (V + Vᵀ)/2‖²_F + ‖(V − Vᵀ)/2‖²_F, and the last term does not depend on Z. The identity needs both the Frobenius norm and a single scalar step. It does not extend by analogy to array steps, to other metrics or to wrappers. Implementation status: #261 is open. At the audited commit prox!(Y, NormL1(0.5), [0 1; 3 0], 1.0) into an owner returns 2.5 for the pair (the lower-triangle entry 3, minus 0.5), while prox!(Y, SqrNormL2(1.0), …) with the same argument throws. The contract's rule (project, with the symmetric part 2 giving 1.5 for the first) is not yet true of the code.
IDRequirement
VAL-1Exact symmetry means _symequal(a, b) = isequal(a, b) || (a == b) === true (src/sparse_iterate.jl:932): NaN matches NaN, 0.0 matches −0.0, 1 matches 1.0. It is structural equality and says nothing about whether a value is admissible: a weight −1 is symmetric and still rejected by the penalty's own domain check. The two checks stay separate.
VAL-2The comparison of a mirrored pair must be made on the source values, before conversion to T. A pair unequal in Float64 that rounds equal in Float32 must be rejected.
VAL-3A coordinate oracle (prox_coordinate!, kkt_violation for k) may inspect only the pair it uses. A stored-only operation may inspect only the pairs it touches. Neither certifies the model.
VAL-4The full validation entry point is ProximalBase.check_symmetric_parameters(f, X), with ProximalBase.entry_parameters(f) as the declaration for extensions. Both must keep their roles. A solver calls it once at creation, on the original caller-supplied penalty and before any transformation of its parameters. A solver must not silently repair an asymmetric parameter (average, or take one triangle), because the library must not choose the caller's interpretation: a half-filled weight matrix may mean "use this triangle", not "average it with zeros". (Averaging does preserve the objective of a weighted L1 penalty on symmetric matrices; that is not the reason for the rule.) Validating the result of such a transformation is too late. The audited ProximalSolvers does the opposite: _symmetric_penalty(g, x::SymmetricSparseIterate) defaults to average = true (src/cd/models.jl:540, _symmetric_average :561), and both workspace constructors call it (src/workspaces.jl:76,99). That behavior conflicts with the amended #142 rule and must change in ProximalSolvers; this contract does not change it.
VAL-5Scope: this redesign promises scalar Frobenius steps γ only for the oracles of §2.9 on an owner. Per-entry step arrays and diagonal metrics on an owner are out of scope, and an array γ should throw an ArgumentError there. This is a scope choice, not a claim that a symmetric diagonal metric destroys coordinate independence. What would be lost: the audited code accepts an exactly symmetric γ matrix in prox! into an owner (run: prox!(Y, NormL1(0.5), [0 3; 3 0], [1 2; 2 1]) gives 2.0, and an asymmetric γ throws), and Tilt's path checks symmetric steps (src/metric.jl:69,77); ProximalSolvers already rejects diagonal preconditioning on an owner (src/solvers/diagonal_metric.jl:23). Scalar steps are validated by the step contract (numerics P1–P3).
VAL-6What invalidates a validation. The check is a statement about the arrays at the time of the call. Mutating any array reported by entry_parameters afterward, in either triangle, invalidates it (arrays symmetric by type, such as Symmetric(W, :L) over a parent the caller mutates, stay symmetric). A caller who mutates parameters re-validates.
VAL-7A custom entry function whose result depends on the index (i, j) without a parameter array (so entry_parameters cannot see it) must itself be symmetric. That responsibility is the extension author's.
VAL-8No public unchecked API and no validation cache is introduced by this contract. The per-call cost of dense-parameter scans (#374) is left to its own issue.

Checked writes. Before the first mutation of X, including its active set, the following must be detected: a shape or axes mismatch; an index out of bounds; a mirrored pair that is unequal under VAL-1/VAL-2; a destination that is not supported (complex element type; the read-only view). The following are not promised: that a conversion which throws (InexactError into an integer T) or an arbitrary user callback leaves X untouched; that a write that fails in the middle of a non-listed way rolls back.

2.11 Performance as a contract

Fixed-width CPU scalar types (Float32, Float64).

IDRequirement
PERF-1After construction, lookup and update by ID or by matrix pair, membership (isactive), and the first activation of a coordinate must be worst-case O(1). This is deterministic indexing, not amortized insertion and not an expected hash lookup.
PERF-2The capacity prerequisite is stated openly: construction reserves room for all q coordinates, so activation never grows storage. Construction time and memory are O(q). "Sparse" does not promise O(s) total storage.
PERF-3Traversal of the active set (activecoordinates, activevalues) must cost O(s) of traversal work. The derivative, cache update and full KKT screening a solver attaches have their own costs and are not covered.
PERF-4Constructing θ, A, activecoordinates(X) and activevalues(X) must not copy X's data.
PERF-5After warm-up, these must not heap-allocate for Float32/Float64 inputs: X[i,j], X[i,j] = v, θ[k], θ[k] = v, isactive, activate! (capacity reserved), prox_coordinate! for a built-in separable f with scalar or Symmetric-typed parameters, and a sweep over activecoordinates(X) that calls it.
PERF-6mul!(y, A, v) for a dense vector v must cost O(p + s) for finite input, including initialization of y. A no-copy wrapper that falls to the dense O(p²) scan does not meet it. For a non-finite v the result must be the same, or the same documented error, before and after dropzeros!: a mathematical product must not depend on whether a zero has a storage slot. (Audited code does not satisfy this: with v = [Inf, 1, 0] and one stored explicit zero at (3,1) the product has a NaN at row 3, and after dropzeros! the same entry is 0.0.) Recommended default: one O(p) scan of v and an ArgumentError for any non-finite entry, so the finite case stays O(p + s). Numerics M1 cites finite linear coefficients and does not settle 0·Inf; the rule must be reconciled with the non-finite policy in docs/src/numerics.md. (Amended by FD-9, iterate-family contract.)
PERF-7dropzeros! must be O(s). Matrix(X) is O(p² + s); copy(X) and similar(X) are O(q).
PERF-8No other generic matrix operation on A is promised to be sparse-fast. Recommended sparse-aware methods: norm, dot, sparse(A), sum. A reader of the specification must not infer more.

The contract names no field, no storage type and no hash table. The audited code uses a direct index table of length q, which meets PERF-1 and PERF-2; that is an implementation, not a promise.

Part 3. Decisions for maintainer sign-off

Each gives a recommended default, one reason and one consequence.

  1. Owner is no longer an AbstractMatrix (OWN-1). Recommend: yes. No inherited generic mutator can reach the owner. Consequence: every Base-generic call on an owner (sum(X), cholesky(X), X * v through AbstractMatrix, x .= …) stops compiling; callers pass matrixview(X) or Matrix(X).
  2. size(X) == (p, p) and no length (OWN-3, OWN-4). Recommend: keep size, leave length undefined. size is unambiguous and used; length has two plausible meanings. Consequence: length(X) is an error.
  3. nnz(X) is removed; nactive(X) replaces it; no matrix-view nnz (ACT-2). Recommend: remove. Its three possible counts differ by up to a factor of two and an audited caller (CovarianceSelection's hard_threshold!) indexes 1:nnz into private storage. Consequence: code that used nnz(X) as a model size writes count(!iszero, activevalues(X)) after dropzeros!, or nactive(X).
  4. Matrix import replaces the working set (CPY-4). Recommend: replace. The result depends only on the argument. Consequence: explicit zeros disappear on import; a warm-start that must keep them uses θ .= ….
  5. New name activevalues (ACT-4). Recommend: add. Two audited packages read or write the first nnz values of private storage by slot (ProximalSolvers' momentum history, CovarianceSelection's hard_threshold!); this is the smallest supported replacement. Consequence: one new exported name, with the handle lifetime of ACT-3.
  6. An active handle is a handle, not a snapshot (ACT-3). Recommend: handle, reacquire after activation or compaction. A snapshot costs O(s) and an allocation per sweep. Consequence: a solver that activates inside a sweep must reacquire; an active-only sweep need not.
  7. Projection of the proximal argument is part of the oracle under a scalar Frobenius step only (§2.10 item 3). Recommend: yes, and not beyond. It is exact there. Consequence: #261 must land for ORC-3 to be true. An array step is not accepted on an owner at all (decision 11, VAL-5), so no projection of the argument under an array step arises.
  8. prox_entry keeps a matrix linear index (IDX-3). Recommend: keep. Weights are matrices. Consequence: the two index spaces still meet in this one function; the docstring must say so.
  9. Public KKT normalization is the entry normalization (§2.8). Recommend: keep. It is comparable across diagonal and off-diagonal coordinates. Consequence: a solver holding a coordinate derivative divides by mₖ before calling.
  10. A matrix-semantic reduction set on owners (ORC-10: norm, norm_diff, dot). Recommend: keep, as today. ProximalSolvers' stopping norm and trial arithmetic need it, and norm(θ) is the wrong number. Consequence: three named methods on the owner outside AbstractArray.
  11. Scalar Frobenius steps only (VAL-5). Recommend: yes. One scope, stated once; no array-step claim to defend. Consequence: symmetric per-entry step arrays that prox! accepts into an owner today are rejected in 0.6.
  12. Solvers validate the caller's original penalty and never repair it (VAL-4). Recommend: yes. The library must not choose the caller's interpretation: a half-filled matrix may mean "use this triangle", not "average it with zeros", even though averaging preserves a weighted L1 objective on symmetric matrices. Consequence: ProximalSolvers' default-averaging _symmetric_penalty must change; users who want the mean write it.
  13. Non-finite v in mul!(y, A, v): error, by default (PERF-6). Recommend: ArgumentError after one O(p) scan. The product then cannot depend on whether a zero has a slot. Consequence: a NaN or Inf in v raises instead of propagating; this needs reconciling with numerics. (Amended by FD-9, iterate-family contract.)
