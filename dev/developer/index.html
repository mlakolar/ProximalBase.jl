Developer Documentation

This section is for contributors and maintainers of ProximalBase.jl: its representation invariants, oracle dispatch, Julia integration, mathematical and numerical contracts, performance constraints, and conformance evidence. For API usage and examples start with Iterates, The interface, and Writing your own function.

The main user path now begins with Function objects and capabilities, Operations on functions, and the Function library. Keep this developer section for invariants, internal dispatch, normative contracts and conformance, not general API discovery.

Authoritative contracts and acceptance criteria

The four iterate-family documents below are rendered in full into the documentation site at build time from docs/design/. The generated pages are not another editable copy of the contract. Links between these contracts are preserved; maintainer amendments in a later contract take precedence where explicitly stated.

Read the status labels. The design documents record 0.6 targets, amendments, tests, and evidence at specific historical commits. A signed-off target is not a claim that every feature has been implemented, that an issue is closed, or that all conformance tests currently pass. The published numerical contract is the normative numerical source; the discussion and decisions in docs/design/numerical-contract/ are supporting records, not a second policy.

The 0.6 iterate-family contract supersedes the earlier FC-11 requirement for SparseIterate specializations of nnz, nonzeros, findnz, and issparse: they were deliberately removed; dropzeros! remains supported. For a method-level inventory see the source audit, which records the source at its audit commit rather than rechecking today's method table.

A separation worth maintaining

  • Storage contracts determine which optimization coordinates exist, their values, activation, copying, and how callers access them.
  • Function contracts determine values, proximal maps, gradients, curvature, restrictions, and KKT screens. A storage type does not acquire these methods merely by implementing coordinates.
  • Numerical contracts determine result precision, non-finite input handling, overflow, aliasing, and observable exceptions within the supported domain.
  • Solver responsibilities include choosing steps, update schedules, stopping criteria, and when to screen or compact a working set.

Do not define a new method as public merely because the implementation uses it. If a contract needs to change, use the contributor process and update the canonical requirement rather than making an independent rule in these explanatory pages.
