Function objects and capabilities

ProximalBase represents a mathematical objective, penalty, or constraint by a function object. Built-in function types are subtypes of AbstractFunction; an object f is callable as f(x). The object contains the mathematical parameters and, where needed, reusable computation state. A solver interacts with it through a common collection of operations, rather than a separate solver implementation for each loss or penalty.

For example, LeastSquaresLoss(y, X) represents a data-fitting loss, NormL1(λ) represents a sparsity penalty, and IndBox(l, u) represents the indicator function of a feasible set. The same regularizer can be used in proximal gradient, coordinate descent or another method that requests its supported oracles. The function does not itself choose the algorithm.

Values, parameters, and composition

A function object specifies what is being computed, not how the solver iterates. For a composite problem,

\[min_x F(x) = f(x) + g(x),\]

f may be a smooth data-fitting loss and g a penalty or an indicator of constraints. The solver selects x, a step size, and the stopping condition; ProximalBase provides operations such as gradient! and prox!.

Built-in types fall into several broad roles:

RoleExamplesRead next
Smooth losses and quadratic functionsLeastSquaresLoss, SqrNormL2, LogisticLoss, QuadraticFunctionSmooth functions
Penalties and regularizersNormL1, ElasticNet, GroupNormL2, NuclearNormPenalties
Constraints as indicator functionsIndBox, IndSimplex, IndPSDSets
Functions built from other functionsScaled, Translate, Constrained, SeparableSumFunctions built from functions

An indicator function is zero at feasible points and infinite outside the set. Its proximal map is a projection. Some mathematical functions are both smooth and proximable: these categories are capabilities, not an exclusive classification. Composition wrappers can preserve, transform, or restrict the oracles of their component functions; compatibility must be checked for the actual wrapper and operands.

Traits and oracles

The public traits answer whether a function has a mathematical or computational property. They do not perform the computation themselves.

TraitMeaningRelevant operations
issmooth(f)Differentiable on the interior of its domaingradient!, value_and_gradient!
isproximable(f)Has a supported, efficiently computed proximal mapprox!, value_and_prox!
isseparable(f)Expressible as a sum of independent entry functionsvalue_entry, prox_entry
isconvex(f)Convexity, used to justify optimization guaranteesProperty, not an oracle
hashessian(f)Supports the second-order interfacehessian_vec!, quadratic_model
haslmo(C)A supported linear minimization oracle for this set instancelmo!, lmo; sometimes lmo_atom
iszeropreserving(f)Separable zero entries can be skipped under its documented conditionsSparse-aware evaluation and proximal kernels

Most capability traits depend on the function's type. haslmo and iszeropreserving are instance-dependent: the bounds or radius of a set, or the parameters of a penalty, can change the answer.

A true trait is not a guarantee of every combination of argument type, backend, or numerical parameter. For instance, a smooth function may lack a finite known lipschitz constant, and a proximable function need not have a special kernel for every array or sparse iterate. The operations guide and individual docstrings give the actual supported domains.

using ProximalBase

f = SqrNormL2(1.0)
g = NormL1(0.5)
x = [2.0, -1.0]

@assert issmooth(f) && isproximable(f)
@assert isproximable(g) && isseparable(g) && isconvex(g)
@assert gradient(f, x) ≈ x
@assert prox(g, x, 1.0) ≈ [1.5, -0.5]
(value = f(x), gradient = gradient(f, x), proximal_point = prox(g, x, 1.0))
(value = 2.5, gradient = [2.0, -1.0], proximal_point = [1.5, -0.5])

Three distinct interfaces

  1. Function operations describe values, derivatives, proximal maps, restrictions, and optimality checks for a mathematical function.
  2. Iterates describe how an algorithm stores and changes optimization coordinates: entries in a SparseIterate, independent symmetric variables in a SymmetricSparseIterate, or groups in an AtomIterate.
  3. Solvers choose an update schedule, steps, momentum, line searches, active-set management, and convergence tests. ProximalBase supplies primitives for these choices, not a general solver interface.

The distinction matters for prox_entry(f, v, i, γ), which addresses entry i of a function's arrays, versus prox_coordinate!(x, f, k, γ), which updates the optimization coordinate k of an iterate. For a grouped iterate one coordinate is a group, not an entry; for a symmetric iterate one coordinate represents an independent variable, not a full-matrix linear index.

To implement your own mathematical function, read Writing your own function. To understand Julia dispatch and the private implementation, read Developer Documentation.
