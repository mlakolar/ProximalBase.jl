Compatibility and migration

The 0.5 interface uses callable function objects, output-first mutating operations, and lowercase coordinate operations. The 0.4 compatibility names remain available with deprecation warnings throughout 0.5 and are scheduled for removal in 0.6. Run existing code with --depwarn=yes to find uses.

The legacy abstract-type bindings alias AbstractFunction; they do not identify smooth or proximable subsets. Query issmooth and isproximable instead.

Matrix products

Use dot(view(A, row, :), b) in place of A_mul_B_row, and dot(view(A, :, row), b) in place of At_mul_B_row. Replace group-product helpers with mul! on view(A, :, G) or its transpose.

For A_mul_X_mul_B, use A * X * B, with X represented as a SparseIterate matrix rather than a vector of its entries. A single entry is dot(view(A, :, r), X, view(B, :, c)) for symmetric real A and B. For A_mul_UUt_mul_B, use (A * U) * transpose(B * U); its entry helper becomes dot(U' * view(A, :, r), U' * view(B, :, c)) in the same real setting.

Group compatibility alias

Existing code may use ProximalBase.AbstractGroupNorm to recognize grouped penalties. This compatibility alias includes GroupMCP and GroupSCAD, so it does not imply convexity or positive homogeneity.

LogisticLoss, PoissonLoss, and HuberLoss are specializations of GLMLoss. IndBallLinf and Constrained are constructor functions that return suitable concrete functions. Avoid dispatch that assumes every exported constructor name is a concrete type.
