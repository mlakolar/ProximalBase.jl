Numerical contract

This page states the retained numerical behavior and its limits. The historical decisions cover a much larger package; they are historical evidence rather than a live capability list. Current source and tests govern the minimal core.

Supported precision and oracle agreement

The supported CPU numerical targets are homogeneous Float64 and homogeneous Float32. In the supported configuration, the floating-point design/response data, iterate or proximal input point, function parameters (such as levels, weights and centers), proximal step, and floating output buffers all use the same type T. Float64 is the primary performance and accuracy target; Float32 is also tested. Individual methods may accept ordinary integer parameters; this is not a promise to coerce arbitrary mixed floating-point arguments.

Mixed Float32/Float64 is not a guaranteed mode. Some current methods still accept it and perform internal promotion, but their return types, numerical accuracy, exceptional-range behavior and performance are implementation-specific. They are not required to reject such calls. A wider data or parameter type does not establish a general promotion rule for the result. Other real types, including BigFloat, are not guaranteed production types. BigFloat remains useful for independent reference tests.

Conversion can lose the range of a mixed-type parameter. The gradient and point-aware KKT scores of SqrNormL2 convert the level and center entries to their working type. The proximal map also converts the center entries to its working type. The value rounds a Float64 center to Float32 for Float32 data, and a center of BigFloat precision to the data type for Float32 or Float64 data. The same center rounding applies during value recovery. The dense unweighted sum paths of NormL1 and NormL1Nonneg convert the level to the data type. Their entrywise fallbacks use the supplied level when the converted level and entries are finite and the product with the sum is nonfinite. An input that rounds to zero, a subnormal, or infinity can therefore change the result even when the exact result is representable.

For supported homogeneous array-function calls:

  • f(x) returns the value in T = float(eltype(x)).
  • Allocating gradient and proximal operations produce their documented representations in T; SymmetricSparseIterate-specific results are described in the symmetric iterate guide.
  • Mutating operations respect the destination's element type and never change the caller's storage type.
  • value_and_gradient!(out,f,x) returns the standalone value at the input x and stores the corresponding gradient in out.
  • value_and_prox!(out,f,x,γ) returns the value at the stored proximal output, including its rounding, not at an unrounded temporary.
  • Exact input/output proximal identity is supported; built-in gradients reject input/output identity. Other partial/derived-view overlap is unsupported.

Some implementations use promoted private scratch or widened arithmetic to improve numerical stability. Those internals do not widen the supported set of caller precision combinations or imply a generic model-precision override for custom functions.

For Float32 calls, explicitly construct floating parameters and steps in Float32, rather than assuming Julia's Float64 literal 0.5 will be treated as a supported Float32 parameter. The array and precision conventions include a homogeneous example for both supported types.

Overflow and underflow of values

The following range guarantees concern finite-data computations. Non-finite inputs and penalty endpoints have separate rules below.

Range guarantees

Ordinary finite calls use efficient numerical paths. Exceptional paths selectively recover representable values when an intermediate product or sum would overflow or underflow. These include scaled square sums, finite-data affine/quadratic values and products of nonnegative level/step/weight factors. SqrNormL2 also recovers gradient differences and proximal convex-combination coefficients. SqrNormL2 and LeastSquaresLoss share one squared-residual recomputation: each residual is formed before scaling (as x/2 - y/2, one binade up, when x - y itself overflows) and the squares are summed in units of the largest one. Genuine NaN/Inf data or parameters keep their ordinary IEEE result; only finite inputs whose intermediates leave the range are recomputed. For the LinearFunction value at a matrix SparseIterate, the finite inputs are d, the nonzero stored entries and the coefficients at them (for a Diagonal coefficient array, the nonzero stored diagonal entries and their coefficients: an off-diagonal NaN or Inf of the iterate is ignored): the recomputation sums their products as exponent-separated terms (as the QuadraticFunction recovery does), collapses the sum and adds d to it in its own units, and a nonfinite coefficient at a zero of the iterate does not prevent it. It reads the nonzero stored entries, O(nactive(x)); for a Diagonal coefficient array it scans the p diagonal positions, O(p), whatever nactive(x) is. At a dense array, a vector SparseIterate and a SymmetricSparseIterate, the recomputation sums the same exponent-separated terms when d, all coefficients and all entries of the argument are finite. Recovery is worthwhile when it changes a materially inaccurate answer into a representable result in the working precision.

The squared-residual recomputation that SqrNormL2 and the least-squares oracles share has the same kind of boundary uncertainty as the NormL2 recomputation below: within a few eps (the relative error bound of the sum) of the overflow threshold floatmax(T) + ulp/2, where ulp is the spacing between floatmax(T) and its predecessor, it does not decide on which side the exact value lies, so a finite answer there is within the error bound of the exact value and floatmax(T) or Inf can be returned for a value that rounds to the other. This was observed for SqrNormL2, Scaled(LeastSquaresLoss, α)(β) and the oracles of the least-squares section.

The LeastSquaresLoss value has one more recovery, which needs β: where the product Xβ overflows although β, X and Y are finite, f(β) and value_and_gradient! attempt to form Xβ again in units of a power of two, without recovering every representable value (the smooth-functions guide gives a counterexample). The oracles at a caller-supplied predictor or residual (ProximalBase.value_from_predictor and the others described with the smooth functions) take the predictor z as given, without β: they recover a value whose squares overflow or underflow and, for the value alone, a difference z - Y that overflows, and a predictor with a non-finite entry gives a non-finite value. For strided Float32 and Float64 vectors, these oracles, f(β) and value_and_gradient! also recompute a value whose ordinary computation α s / 2 is above floatmax(T)/2, so that the error of the ordinary sum of squares, which grows with the length, does not decide between a finite value and Inf.

The accuracy of a recovered value is an absolute bound B = 4 n eps (sum |terms| + |d|) for n terms. It is a statement about the computed value when the exact value plus B is within the range (|exact| + B <= floatmax). When B exceeds the representable range, there is no guarantee of a finite output. Extreme cancellation among products far beyond the output range (about 2^1077 for Float64, 2^150 for Float32 data) can return an infinity although the exact result is a finite, normal number, in the recovery of a dense argument and in the recovery of the LinearFunction value at a matrix SparseIterate alike (#907). A small d beside a dot that cancels exactly is returned as d when the compensated sum of the products cancels to zero, which is not guaranteed for products of very different sizes.

For NormL1 value recovery, including subnormal terms, see the NormL1 range clauses.

For nonnegative ℓ₁ value recovery, see the NormL1Nonneg range clauses.

For ElasticNet value recovery, its stated bounds and the retained implementation details, see ElasticNet range clauses.

NormL2 values recompute a sum of squares that overflows or falls below the normal range from the squared-residual kernel above, in units of the largest stored entry. On a SparseIterate and a SymmetricSparseIterate both the ordinary sum and that recomputation visit the stored entries only, each off-diagonal symmetric coordinate twice (#808). NormL2, GroupNormL2 and GroupNormLinf values, and their fused values, may recompute a value at or above floatmax(T)/2 in power-of-two units, with sums accumulated in at least Float64. Within a few eps of the overflow threshold floatmax(T) + ulp/2 that recomputation does not decide on which side the exact value lies, so a value that rounds to floatmax(T) may be returned as Inf, or the reverse: the same limit as the other recoveries above (#904).

For IndBallL2, the value and projection compare the norm with the radius in scaled units when the ordinary sum of squares overflows or is too small. The domain has no fixed feasibility tolerance. Within the rounding error of the norm, the comparison can fall on either side of the boundary. value_and_prox! evaluates the stored point. For dense vectors of four entries with matching Float32 or Float64 input, output and radius, the projection checks the rounded coefficients when the input sum of squares is ordinary and the finite radius is at least 2sqrt(4floatmin(T) / eps(T)). If the rounded coefficients fail the comparison, it scales them once more toward zero. The stored point in that case passes the same norm comparison. Other projections can return a stored point outside the computed boundary, giving Inf in the fused call. A positive finite radius projects a NaN input to an all-NaN output, including implicit zeros of a SparseIterate.

See the IndBallL1 numerical contract for ℓ₁-ball feasibility, power-of-two scaling, and tiny-radius projection.

GroupNormL2 values apply the same check to their group terms λ0*w[k]*‖x[G_k]‖₂, and recompute a sum below K*floatmin(T) for K groups from the terms' exponents. GroupNormLinf values apply the same check to their group terms λ0*w[k]*max|x[G_k]|, each formed in floating point as (λ0*w[k])*m with two rounded products when λ0*w[k] is a normal number (and by the three-factor kernel otherwise) and then converted to the output type, and may recompute from the exponents of w[k]*max|x[G_k]| with λ0 applied once. The proximal operators of GroupNormL2 recompute, for finite inputs, a group norm whose sum of squares overflows or underflows and a threshold γ*λ0*w[k] outside the range, in power-of-two units; the ordinary path needs a normal threshold and a normal sum of squares, and is otherwise unchanged.

The clip level τ of NormLinf has an absolute error. On the ordinary finite path, for n ≥ 1 entries in the floating type T of the output with n eps(T) ≤ 1/2 (up to 2^22 entries in Float32 and 2^51 in Float64), a hypothesis that the code does not check, the level returned by the threshold satisfies |τ - τ*| ≤ 2.25 n eps(T) max|xᵢ| + 2nδ, where τ* is the root of Σ(|xᵢ| - τ)₊ = a for the entries abs(convert(T, xᵢ)) and the radius a that the prox forms (the product γλ rounded in the promoted type of γ, λ and T, then to T), and δ = nextfloat(zero(T)) (the storage of a subnormal radius or output adds δ; x = [δ], λ = δ, γ = 0.5 gives [δ] where the exact point is δ/2). The prox clips at the larger of the level and zero, which is within the same bound of max(τ*, 0). The derivation, in src/functions/normlinf.jl, bounds the excess Σ(|xᵢ| - τ)₊ - a for each of the four ways the threshold search ends, and it does not assume that the entries it found above the level are the entries above the exact level. Unlike the relative bounds of the NormL2 and GroupNormL2 kernels, the bound is absolute: an entry far below max|xᵢ| is not clipped to a relative accuracy. A sum of magnitudes that overflows or exceeds floatmax(T)/2 is processed in power-of-two units: the statement above then applies first to the scaled entries and the scaled radius, as they are rounded, and converting back carries the scaling allowances described here (the radius γλ rounded to T can itself be infinite there, as for x = [M, M], λ = 1.5, γ = M with M = floatmax(T), which is not the reference of the bound). The subnormal losses of the scaling are below the nominal scale n eps(T) max|xᵢ| under the same hypothesis on n, and the scaling of an entry or of the radius changes it by at most one subnormal spacing (the allowance covers the ldexp of Julia 1.10 noted above), a second hypothesis of that argument that the code does not check. Through Scaled, the wrapper's recovery of a radius γλα beyond the range has a limit: for Scaled(NormLinf(2.0 * 2.0^-1000), 2.0^1000) at the step 0.75 floatmax(Float64) on two entries equal to floatmax(Float64), even the folded level at half the scale is out of range, the wrapper passes an infinite step, and the output is +0 where the exact result is about floatmax/4. For positive finite level and step, an infinite entry without NaN gives the identity; on the finite clipping branch the value is λ τ, computed from the largest stored magnitude τ, and value_and_prox! returns the value of the stored output, computed as f(y) computes it. GroupNormLinf clip accuracy

For GroupNormLinf, let T be the common type of the input, output, level, weights and step (Float32 or Float64). For finite data and positive finite parameters in round-to-nearest arithmetic with gradual underflow, each stored entry is within 8 n eps(T) M + (2n + 1)δ of the exact proximal entry for r = γλ0w[k]. Here n ≥ 1 is the size of the group, M its largest magnitude and δ = nextfloat(zero(T)). The bound assumes n eps(T) ≤ 1/2, which the code does not check. This applies to the direct array and compact block calls. The parameter precedence for zero and infinite factors is given in the table below.

The exact nonnegative level at radius r is the maximum of zero and the levels (sum(abs(x[i]) for i in A) - r) / length(A) over nonempty subsets A of the group. Thus it changes by at most the largest entry perturbation and the absolute radius perturbation. A relative perturbation of the radius by at most η changes the level by at most η M / (1 - η): at the smaller radius a subset with a positive level has radius per entry at most M. The radius uses two products in the working type, or two products of significands followed by exponent scaling if the normal-range products cannot be used. With u = eps(T)/2, the two products contribute at most 4u M to the level error and subnormal radius rounding at most δ, including the Julia 1.10 ldexp allowance above.

If the computed radius is below the computed sum, the shared threshold contributes at most 4.5 n u M + 2nδ before accounting for the radius error. If the computed radius reaches the computed sum, that sum is at least (1 - (n - 1)u) times the exact sum. The subset formula then bounds the level for the computed radius by (n - 1)u M. If the rounded radius overflows in these units, the exact radius exceeds floatmax(T)/(1 + u)^2. The exact sum is at most 2 floatmax(T)/3 when its computed value is at most floatmax(T)/2, so zero is then the exact result.

If the first sum exceeds F/2, where F = floatmax(T), the group is read in units of 2^-k with k = ceil(log2(n)) + 2. Under the size hypothesis the rounded scaled sum is at most (F/4 + nδ)/(1 - n u) < F/2, so the first scaling suffices. The scaled entries incur at most δ of perturbation in those units. Applying the unscaled bound there and multiplying back gives (4.5n + 4)u M plus at most 2^k [(2n + 2) + (4.5n + 4)u]δ. Since 2^k < 8n, the latter term is at most 48 n^2 δ. The scaling trigger requires M > F/(3n), and 144 n^2 δ ≤ u F for Float32 and Float64 under the size hypothesis, so this term is at most n u M. Scaling the level back is exact where finite. Capping it at M, including when it overflows, can only decrease the error. Clipping selects an entry or the signed level, both already in T, so same-type storage adds no rounding error. With a different input or output type, entries are read in the floating type of the destination and the clipped values are converted to its element type on write.

These are practical numerical safeguards, not a promise of exhaustive range recovery or correctly rounded arbitrary reductions, gradients, or matrix products. When the final mathematical value itself is out of range, an appropriate infinity or underflow to zero may be unavoidable, subject to the function's endpoint semantics. There is no cross-platform or cross-version bitwise arithmetic-order guarantee.

Routes that compute the same proximal point, such as the array prox! and the scalar prox_block, are not guaranteed to agree bit for bit. For homogeneous Float32 or Float64 inputs with γλ between floatmin(T) and 2^125 (Float32) or 2^1021 (Float64), the centered SqrNormL2 proximal point evaluates the coordinates whose argument and center entries have the same sign bit with muladd, which the compiler may or may not contract into one rounding, depending on how it optimizes each call site and on the CPU. On Julia 1.13.4 and an x86-64 CPU with fused multiply-add, with γλ < 1, prox_block was observed to contract it and the vectorized loop of prox! not to, so the two differed in the last place. Both are rounded evaluations of the same formula; the tests compare the two routes within one unit in the last place on selected inputs.

The order in which an ordinary value adds its terms is not part of the contract either. The unweighted NormL1 value of a dense Float32 or Float64 array of 16 to 1024 entries, and the NormL2 value of such an array or strided view, add their terms in one vectorized loop. Julia's sum is also one vectorized loop up to 1024 entries, so the rounding error is of the same kind and grows with the length in the same way, but the result can differ from λ0 * sum(abs, x) or λ * sqrt(sum(abs2, x)) in the last place. The tests bound these values against a high-precision sum and do not compare their bits; shorter and longer arrays use sum.

using ProximalBase
λ = 2.0^-1022
f = SqrNormL2(λ,[-2.0^1023])
x = [2.0^1023]
@assert gradient(f,x) == [4.0]
z = prox(SqrNormL2(2.0^800),[2.0^900],2.0^800)
@assert z == [2.0^-700]
reference = setprecision(BigFloat,256) do
    Float64(big(2.0)^900 / (1 + big(2.0)^1600))
end
@assert z[1] == reference

Nested positive finite Scaled factors can retain their exponent sum so an overflowed/underflowed intermediate scale does not discard a recoverable leaf result. This mechanism is implemented for retained kernels, not synthesized for custom functions.

For NormL1 and NormL1Nonneg under Scaled with a positive finite scalar step (Float32 or Float64 factors, step and level), the product αγ of the factors and the step can be below floatmin(T) or above floatmax(T) while the threshold αγλ0wᵢ of an entry is representable, because its weight brings the product back into range. The level that holds the factors and the exponent of the step, which is αγλ0 divided by the significand of γ, is not a normal number when it is zero, when it is subnormal, and when it overflows, which can happen although αγλ0 is at most floatmax(T). In these cases the exponent is split between the level and the step when the step and the level of that split are both normal numbers (the first limit below says when they are not), and the leaf forms the threshold of each entry from them and its weight, so that the weight can bring it back into range. For Scaled(Scaled(NormL1(1.3 * 2.0^20, [2.0^1013]), 2.0^-531), 2.0^-531), the step 2.0^-30 and x = [3 * 2.0^-50], the threshold is 2.2551405187698493e-18 and the scalar step gives [2.662280118581606e-15], as the array step does. The tests compare the proximal point with the point given by the exact threshold, within four units in the last place of the point, on selected inputs and on a seeded sweep over the exponents of the factors, the step, the level and the weight. Two limits, each on its own:

  • When the step or the level of the split is not a normal number, which happens for αγλ0 near or beyond the square of a range limit of the type (floatmin(T)^2, floatmax(T)^2), the exponent is not split and the step is passed rounded (zero, a subnormal number or Inf), as before.
  • ElasticNet keeps the earlier route. Under the same conditions, on either side of the range (αγ below floatmin(T) or above floatmax(T)), also with λ2 = 0, and with a single factor, a scalar step can lose the ℓ₁ threshold where the same step passed as an array of steps gives it. With ElasticNet(1.3 * 2.0^20, 0.0, [2.0^1013]) in place of the NormL1 above, the scalar step gives [2.6623668547554047e-15] and the array step [2.662280118581606e-15].

The dedicated Scaled(ElasticNet(...), α) limitation and its examples are retained in ElasticNet limitations.

NaN, infinities and zeros

There is no universal non-finite endpoint rule or universal step validator. The mathematical prox uses positive finite γ. Many retained closed forms accept zero, negative, infinite or NaN steps and apply their established arithmetic; acceptance does not establish a meaningful proximal minimizer in those cases. Decomposition-based methods are intended for finite data and ordinary valid steps. Do not pass arbitrary non-finite data into them expecting a uniform all-NaN result or a particular exception.

Cardinality penalty endpoints

For NormL0(λ) at positive finite λ and γ, compare the squared distance cost of setting a finite input v to zero with the penalty cost of keeping it. The comparison uses the exact products of the represented homogeneous Float32 or Float64 inputs. A tie gives positive zero, including when the candidate costs fall outside the floating-point range.

Level and valid stepProximal entry
λ = 0, including at γ = InfIdentity
λ = Inf, including at γ = 0Positive zero
0 < λ < Inf, γ = 0Identity
0 < λ < Inf, γ = InfPositive zero
0 < λ < Inf, 0 < γ < InfHard thresholding for finite inputs. NaN and signed infinities pass through

At a zero level the value is zero, including for NaN input. At a positive level, a NaN entry gives a NaN value (E2, #560). Either infinity is a nonzero entry. With fixed positive finite level and step, the signed infinity output follows the limit from finite inputs (E3, #469). The constant-zero map at an infinite step is the endpoint convention. The value sums the entry contributions in the result precision, which can incur rounding.

Direct array oracles reject negative and NaN steps before writing. Array steps are matched by linear index and checked in full, with work proportional to their length. A scalar step is required for a symmetric sparse iterate output. Value and scalar-step proximal calls between same-kind sparse iterates traverse stored entries, with the value counting each symmetric off-diagonal entry twice. A sparse iterate can omit a zero from storage and read it back as positive zero. Fused calls return the value at the stored output. Use a nonnegative, non-NaN step with prox_block and in calls through Scaled.

Infinite penalties at zero step

For NormL1(Inf, w), the γ = 0 endpoint is lim_{γ→0+} prox_{γf}(x) with the function f held fixed. That function is the indicator of {0} in each coordinate with w[i] > 0 (an infinite w[i] included) and is zero in each coordinate with w[i] = 0, so the limit is the projection onto the closure of its domain: positive-weight coordinates become exactly +0, even for NaN or ±Inf inputs, and zero-weight coordinates are returned as soft thresholding by a zero threshold returns them (NaN and ±Inf unchanged). Unweighted NormL1(Inf) therefore maps every coordinate to +0. The order of limits matters: for a fixed finite level, shrink(x, γλ) → x as γ → 0+, but NormL1(Inf) is already the constraint at every positive step, so the result is not computed as shrink(x, 0⋅Inf). Among the NormL1 parameters, this rule is specific to the infinite overall level. An infinite coordinate weight at a finite level keeps the narrower #853 rule above (finite inputs fixed; non-finite inputs may give NaN), and finite factors whose product overflows are never treated as an infinite level (the finite-threshold limitation above). For finite levels and finite weights, γ = 0 keeps the identity. A finite positive Scaled factor passes the zero step through, so 2 * NormL1(Inf) projects as well; an infinite factor at a zero step forms the step Inf⋅0 = NaN in the wrapper before NormL1 sees it, and follows the wrapper's existing step arithmetic. ElasticNet follows this rule for an infinite λ1, and implements the same zero-step projection for an infinite ridge level λ2, the indicator of {0} in every coordinate. NormL1Nonneg applies it to an infinite level (positive-weight entries become +0; zero-weight entries are projected onto the orthant, not left unchanged). GroupNormL2 and GroupNormLinf apply the same reading at γ = 0 to an infinite level (groups with a positive weight become +0) and to an infinite group weight. NormL0, NormL2 and NormLinf apply it to an infinite level. No other function is claimed to implement a zero-step projection rule.

Signed zeros do not activate absent coordinates; explicit active signed zeros can be retained in storage. Symmetric-iterate isequal distinguishes stored negative zero from absent positive zero; == does not. dropzeros! removes either signed zero and preserves NaN/Inf.

Sparse product semantics

The specialized products in the operation table ignore zero iterate coefficients, stored or absent. No term is formed even if the other operand at that coordinate is NaN/Inf. A nonzero NaN/Inf coefficient contributes ordinarily. A zero in a dense factor remains an IEEE zero. A coordinate view uses ordinary dense-vector semantics instead.

using ProximalBase, LinearAlgebra
x = SparseIterate(2)
x[1] = 2
activate!(x,2)
v = [3.0,Inf]
@assert dot(v,x) == 6
@assert isnan(dot(v,coordinates(x)))
dropzeros!(x)
@assert dot(v,x) == 6
dot(v,x)
6.0

The LinearFunction value at a matrix SparseIterate follows the same rule, as its own computation and not through dot(c, x): a position that is not stored, or is stored as +0 or -0, contributes nothing and c is not read there, so a NaN or ±Inf coefficient at it does not reach the value, while a nonzero entry keeps ordinary arithmetic. For a dense c that is not a Diagonal, f(Matrix(x)) takes the dense IEEE dot and gives NaN for such a coefficient.

using ProximalBase, LinearAlgebra
x = SparseIterate(2, 2)
x[1, 1] = 2
activate!(x, 4)                    # the entry (2, 2) is stored as a zero
c = [1.0 NaN; Inf 1.0]
f = LinearFunction(c, 0.25)
@assert f(x) == 2.25
@assert isnan(f(Matrix(x)))
f(x)
2.25

Five-argument products with β=0 overwrite the destination without reading its old numerical entries; α=0 scales/clears output without reading right-operand values, after required type/shape/alias checks. Finite summation can depend on activation order; compaction can therefore change final rounding.

The direct A*X*B kernels for matching Float32/Float64 Symmetric-strided factors and matrix iterate X recover the range of individual finite three-factor terms. They promise accuracy within one neighboring floating value for a normal term, or one spacing for a subnormal term, not correct rounding. A non-finite sum is recomputed in scaled units only when all contributing factors are finite; true NaN/Inf data keep ordinary IEEE outcomes. Tiny terms can be rounded away beside large ones. Other mixed/generic product routes do not inherit this specific guarantee.

Validation, aliasing and evidence

Predictable type/shape/parameter errors precede built-in oracle output writes. A read, conversion or numerical failure can leave output changed. Storage state copies and matrix imports have distinct guarantees documented in views and aliasing. Parameter arrays are not made immutable or copied by validation.
