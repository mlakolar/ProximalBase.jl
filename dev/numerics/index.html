Numerical contract

This page states the retained numerical behavior and its limits. The historical decisions cover a much larger package; they are historical evidence rather than a live capability list. Current source and tests govern the minimal core.

Supported precision and oracle agreement

The supported CPU numerical targets are homogeneous Float64 and homogeneous Float32. In the supported configuration, the floating-point design/response data, iterate or proximal input point, function parameters (such as levels, weights and centers), proximal step, and floating output buffers all use the same type T. Float64 is the primary performance and accuracy target; Float32 is also tested. Individual methods may accept ordinary integer parameters; this is not a promise to coerce arbitrary mixed floating-point arguments.

Mixed Float32/Float64 is not a guaranteed mode. Some current methods still accept it and perform internal promotion, but their return types, numerical accuracy, exceptional-range behavior and performance are implementation-specific. They are not required to reject such calls. A wider data or parameter type does not establish a general promotion rule for the result. Other real types, including BigFloat, are not guaranteed production types. BigFloat remains useful for independent reference tests.

For supported homogeneous array-function calls:

  • f(x) returns the value in T = float(eltype(x)).
  • Allocating gradient and proximal operations produce their documented representations in T; SymmetricSparseIterate-specific results are described in the symmetric iterate guide.
  • Mutating operations respect the destination's element type and never change the caller's storage type.
  • value_and_gradient!(out,f,x) returns the standalone value at the input x and stores the corresponding gradient in out.
  • value_and_prox!(out,f,x,γ) returns the value at the stored proximal output, including its rounding, not at an unrounded temporary.
  • Exact input/output proximal identity is supported; built-in gradients reject input/output identity. Other partial/derived-view overlap is unsupported.

Some implementations use promoted private scratch or widened arithmetic to improve numerical stability. Those internals do not widen the supported set of caller precision combinations or imply a generic model-precision override for custom functions.

For Float32 calls, explicitly construct floating parameters and steps in Float32, rather than assuming Julia's Float64 literal 0.5 will be treated as a supported Float32 parameter. The array and precision conventions include a homogeneous example for both supported types.

Overflow and underflow of values

The following range guarantees concern finite-data computations. Non-finite inputs and penalty endpoints have separate rules below.

Range guarantees

Ordinary finite calls use efficient numerical paths. Exceptional paths selectively recover representable values when an intermediate product or sum would overflow or underflow. These include scaled square sums, finite-data affine/quadratic values and products of nonnegative level/step/weight factors. SqrNormL2 also recovers gradient differences and proximal convex-combination coefficients. SqrNormL2 and LeastSquaresLoss share one squared-residual recomputation: each residual is formed before scaling (as x/2 - y/2, one binade up, when x - y itself overflows) and the squares are summed in units of the largest one. Genuine NaN/Inf data or parameters keep their ordinary IEEE result; only finite inputs whose intermediates leave the range are recomputed. For the LinearFunction value at a matrix SparseIterate, the finite inputs are d, the nonzero stored entries and the coefficients at them (for a Diagonal coefficient array, the nonzero stored diagonal entries and their coefficients: an off-diagonal NaN or Inf of the iterate is ignored): the recomputation sums their products as exponent-separated terms (as the QuadraticFunction recovery does), collapses the sum and adds d to it in its own units, and a nonfinite coefficient at a zero of the iterate does not prevent it. It reads the nonzero stored entries, O(nactive(x)); for a Diagonal coefficient array it scans the p diagonal positions, O(p), whatever nactive(x) is. At a dense array, a vector SparseIterate and a SymmetricSparseIterate, the recomputation sums the same exponent-separated terms when d, all coefficients and all entries of the argument are finite. Recovery is worthwhile when it changes a materially inaccurate answer into a representable result in the working precision.

The squared-residual recomputation that SqrNormL2 and the least-squares oracles share has the same kind of boundary uncertainty as the NormL2 recomputation below: within a few eps (the relative error bound of the sum) of the overflow threshold floatmax(T) + ulp/2, where ulp is the spacing between floatmax(T) and its predecessor, it does not decide on which side the exact value lies, so a finite answer there is within the error bound of the exact value and floatmax(T) or Inf can be returned for a value that rounds to the other. This was observed for SqrNormL2, Scaled(LeastSquaresLoss, α)(β) and the oracles of the least-squares section.

The LeastSquaresLoss value has one more recovery, which needs β: where the product Xβ overflows although β, X and Y are finite, f(β) and value_and_gradient! attempt to form Xβ again in units of a power of two, without recovering every representable value (the smooth-functions guide gives a counterexample). The oracles at a caller-supplied predictor or residual (ProximalBase.value_from_predictor and the others described with the smooth functions) take the predictor z as given, without β: they recover a value whose squares overflow or underflow and, for the value alone, a difference z - Y that overflows, and a predictor with a non-finite entry gives a non-finite value. For strided Float32 and Float64 vectors, these oracles, f(β) and value_and_gradient! also recompute a value whose ordinary computation α s / 2 is above floatmax(T)/2, so that the error of the ordinary sum of squares, which grows with the length, does not decide between a finite value and Inf.

The accuracy of a recovered value is an absolute bound B = 4 n eps (sum |terms| + |d|) for n terms. It is a statement about the computed value when the exact value plus B is within the range (|exact| + B <= floatmax). When B exceeds the representable range, there is no guarantee of a finite output. Extreme cancellation among products far beyond the output range (about 2^1077 for Float64, 2^150 for Float32 data) can return an infinity although the exact result is a finite, normal number, in the recovery of a dense argument and in the recovery of the LinearFunction value at a matrix SparseIterate alike (#907). A small d beside a dot that cancels exactly is returned as d when the compensated sum of the products cancels to zero, which is not guaranteed for products of very different sizes.

NormL1 values also recover terms λ0*w[i]*abs(x[i]) that round into the subnormal range, which loses accuracy even when the total is normal (#373). Each such rounding loses at most half the smallest subnormal spacing, eps(T)*floatmin(T)/2, so an ordinary sum s ≥ n*floatmin(T) of n terms loses at most eps(T)/2 relative to s and is returned from the unchanged vectorized loop. A smaller sum, a zero one included, is recomputed: the products w[i]*abs(x[i]) are accumulated with their exponents, and λ0 is applied before the single conversion to T. This holds for dense arrays and for the stored entries of SparseIterate, BlockIterate and SymmetricSparseIterate, and for value_and_prox! at its stored output. Zero and infinite levels, infinite weights and NaN/Inf entries keep the rules below. Under an infinite Scaled factor a recovered positive value gives Inf, as the folded level NormL1(Inf, w) does; before #373 a value whose terms all rounded to zero gave NaN there. An exactly zero value still gives 0.

ElasticNet values are the value of the ℓ₁ part, computed as NormL1 computes it, plus the value of the ridge part, computed as SqrNormL2 computes it, each with the recovery above, then one addition; on sparse and symmetric iterates both parts read the stored entries only, and on a BlockIterate its storage. On a dense Float32 or Float64 Array with parameters of its type, a single pass over the entries is returned instead when a test on its sum bounds its relative error by (n + 2) eps(T) for n ≤ 1/(2 eps(T)) - 2 entries; the bound is proved in a comment next to the code (src/functions/elasticnet.jl). With both levels positive and finite, a sum of the two parts below 2 floatmin(T) (each part rounded on its own) is recomputed: the terms of both parts are added in one exponent-sum accumulator, as the NormL1 recomputation adds its terms, and the sum is rounded once. For N nonzero terms (λ1*w[i]*abs(x[i]) and λ2*x[i]^2/2, up to two per entry and three per off-diagonal coordinate of a symmetric iterate), with u half the epsilon of the accumulator (Float64 for Float32 data) and N u < 1, the hypothesis of the summation bound used, the result is within (γ_3 + (γ_{N-1}^2 + N 2^-1070)(1 + γ_2)) V of the exact value V plus half a spacing of T at the result (γ_m = m u/(1 - m u)), as proved next to the code, which is below the worst case of the separate parts. On Julia 1.10 ldexp returns 0 for a Float64 result in [δ/2, δ), δ the smallest subnormal (#896), and the final term of the bound is a whole spacing; ElasticNet(2.0^-538, 1.0)([2.0^-537]) is 2.0^-1074. Only a value whose stored entries are all zero keeps its sum. Under Scaled, the value of an ElasticNet is recovered as for any function with levels. For a finite positive factor, where that gives no finite value, or 0 at a point where the function is not exactly 0, the scaled values of the ℓ₁ part and of the ridge part, each rounded on its own, are added; the sum replaces that result if it is finite after conversion to its type, and the first result is kept otherwise. Where one part dominates, the test can pass although the other part alone would be recomputed (ℓ₁ terms below floatmin(T) beside a normal ridge part, or squares below floatmin(T) beside a normal ℓ₁ part). Its proximal point soft thresholds by the threshold of the NormL1 kernel and multiplies by the ridge factor 1/(1 + γλ2) of the SqrNormL2 kernel, both formed from the unrounded factors, so a factor γλ2 outside the range still acts on a representable result.

NormL2 values recompute a sum of squares that overflows or falls below the normal range from the squared-residual kernel above, in units of the largest stored entry. On a SparseIterate and a SymmetricSparseIterate both the ordinary sum and that recomputation visit the stored entries only, each off-diagonal symmetric coordinate twice (#808). NormL2 and GroupNormL2 values, and their fused values, recompute a value at or above floatmax(T)/2 in power-of-two units, with sums accumulated in at least Float64. Within a few eps of the overflow threshold floatmax(T) + ulp/2 that recomputation does not decide on which side the exact value lies, so a value that rounds to floatmax(T) may be returned as Inf, or the reverse: the same limit as the other recoveries above (#904). GroupNormL2 values apply the same check to their group terms λ0*w[k]*‖x[G_k]‖₂, and recompute a sum below K*floatmin(T) for K groups from the terms' exponents. Its proximal operators recompute, for finite inputs, a group norm whose sum of squares overflows or underflows and a threshold γ*λ0*w[k] outside the range, in power-of-two units; the ordinary path needs a normal threshold and a normal sum of squares, and is otherwise unchanged.

The clip level τ of NormLinf has an absolute error of order n eps(T) max|xᵢ| + δ for n entries in the floating type T of the output, with δ = nextfloat(zero(T)) (from the running sums of Condat's algorithm and the storage of a subnormal radius or output), unlike the relative bounds of the NormL2 and GroupNormL2 kernels: an entry far below max|xᵢ| has no relative guarantee, and x = [δ], λ = δ, γ = 0.5 gives [δ] where the exact point is δ/2. A sum of magnitudes that overflows or exceeds floatmax(T)/2 is processed in power-of-two units, whose subnormal losses are below the nominal scale n eps(T) max|xᵢ| when n eps(T) ≤ 1/2 (up to 2^22 entries in Float32 and 2^51 in Float64) and the scaling of an entry or of the radius changes it by at most one subnormal spacing (the allowance covers the ldexp of Julia 1.10 noted above), two hypotheses of that argument that the code does not check. Through Scaled, the wrapper's recovery of a radius γλα beyond the range has a limit: for Scaled(NormLinf(2.0 * 2.0^-1000), 2.0^1000) at the step 0.75 floatmax(Float64) on two entries equal to floatmax(Float64), even the folded level at half the scale is out of range, the wrapper passes an infinite step, and the output is +0 where the exact result is about floatmax/4. For positive finite level and step, an infinite entry without NaN gives the identity; on the finite clipping branch the value is λ τ, computed from the largest stored magnitude τ, and value_and_prox! returns the value of the stored output, computed as f(y) computes it. Endpoint precedence is given in the table below.

These are practical numerical safeguards, not a promise of exhaustive range recovery or correctly rounded arbitrary reductions, gradients, or matrix products. When the final mathematical value itself is out of range, an appropriate infinity or underflow to zero may be unavoidable, subject to the function's endpoint semantics. There is no cross-platform or cross-version bitwise arithmetic-order guarantee.

The order in which an ordinary value adds its terms is not part of the contract either. The unweighted NormL1 value of a dense Float32 or Float64 array of 16 to 1024 entries, and the NormL2 value of such an array or strided view, add their terms in one vectorized loop. Julia's sum is also one vectorized loop up to 1024 entries, so the rounding error is of the same kind and grows with the length in the same way, but the result can differ from λ0 * sum(abs, x) or λ * sqrt(sum(abs2, x)) in the last place. The tests bound these values against a high-precision sum and do not compare their bits; shorter and longer arrays use sum.

using ProximalBase
λ = 2.0^-1022
f = SqrNormL2(λ,[-2.0^1023])
x = [2.0^1023]
@assert gradient(f,x) == [4.0]
z = prox(SqrNormL2(2.0^800),[2.0^900],2.0^800)
@assert z == [2.0^-700]
reference = setprecision(BigFloat,256) do
    Float64(big(2.0)^900 / (1 + big(2.0)^1600))
end
@assert z[1] == reference
z

Nested positive finite Scaled factors can retain their exponent sum so an overflowed/underflowed intermediate scale does not discard a recoverable leaf result. This mechanism is implemented for retained kernels, not synthesized for custom functions.

A known limitation (#567): for Scaled(ElasticNet(λ1, λ2, w), α) with finite levels, a finite positive α and a positive finite scalar step γ whose product αγ is above floatmax, prox, prox!, prox_block and value_and_prox! can return 0 where the exact result is representable. A representable result does not need a representable coefficient. With λ1 = 0, α = γ = 2.0^600 and x = [2.0^1000], the coefficient αγλ2 is 2^1300 for λ2 = 2.0^100, above floatmax, while the quotient x/(1 + αγλ2), about 2^-300, is representable, and the result is 0. For λ2 = 2.0^-1000 and x = [4.0] the coefficient is 2^200 and the result is the representable 4/(1 + 2^200). Scaled(SqrNormL2(λ2), α) also returns 0 in the first case. In some cases the same step passed as an array of steps gives the representable result, for example in the first case and in its Float32 analogue (λ2 = 2.0f0^80, α = γ = 2.0f0^80, x = [2.0f0^127]); for λ2 = 2.0^880 and x = [2.0^1023], with the same α and γ, both steps give 0 where the result is 2^-1057:

s = Scaled(ElasticNet(0.0, 2.0^100), 2.0^600)
prox(s, [2.0^1000], 2.0^600)      # [0.0]
prox(s, [2.0^1000], [2.0^600])    # [4.909093465297727e-91], about 2^-300
t = Scaled(ElasticNet(0.0, 2.0^880), 2.0^600)
prox(t, [2.0^1023], 2.0^600)      # [0.0]
prox(t, [2.0^1023], [2.0^600])    # [0.0]; the result is 2^-1057

NaN, infinities and zeros

There is no universal non-finite endpoint rule or universal step validator. The mathematical prox uses positive finite γ. Many retained closed forms accept zero, negative, infinite or NaN steps and apply their established arithmetic; acceptance does not establish a meaningful proximal minimizer in those cases. Decomposition-based methods are intended for finite data and ordinary valid steps. Do not pass arbitrary non-finite data into them expecting a uniform all-NaN result or a particular exception.

kkt_violation(f,v,x,k) and kkt_violation(f,v,x), GroupNormL2 and NormL2: accuracyIn the ordinary range, which is when the sums of squares of x_G and of the residual are finite and at least n floatmin(W)/eps(W) for a block of n entries and c/norm(x_G) is finite, a nonzero block is computed after the scan for a zero block by two arithmetic passes: the norm of the point (t = c/√Σxⱼ²), then the norm of the residual (√Σ(vⱼ + t xⱼ)²). To first order in n u, with u = eps(W)/2, its error is at most (n + 8) u (norm(v_G) + c), where c is the coefficient as rounded to W. Rounding λ0 w to W adds a relative u for a normal finite product and an absolute term of the subnormal spacing where the product is subnormal or rounds to zero. The bound is relative to the size of the terms that cancel near stationarity, not to the score. The tests use this bound, plus the subnormal spacing of W, for zero blocks as well. The test of the ordinary range is on the sums, not on single entries: a block with a subnormal entry whose sums are ordinary stays on the ordinary path. Outside it (sums that overflow or underflow, a very large c) the block is computed in the recovery type (at least Float64) from the entries read in W, with the norm of x_G and the factor c/norm(x_G) kept as a significand and an exponent: this extends the range of the computation, not its precision, and the result is rounded once to W. The residuals are scaled by the exponent of the largest one so that the accumulated squares do not overflow; a scaled square far below the largest can underflow below the rounding scale of the norm. The Float32 and Float64 calls on arrays allocate nothing in either range (measured by the tests)

Decision on NormL1 non-finite inputs (#853 and #866). A genuinely infinite coordinate weight maps a finite input value to zero, even at zero level and step. For inputs of NaN or ±Inf with finite level, that fixed-zero guarantee is intentionally not extended: retained soft-threshold arithmetic may return NaN. Separately, a threshold made from finite factors can overflow to Inf; with an input of ±Inf, the current result can likewise be NaN even though the mathematical threshold is finite. These examples characterize present behavior, not additional non-finite-output guarantees. A genuinely infinite level at any nonnegative step retains its distinct fixed-zero rule for positive weights, including non-finite inputs; see the zero-step rule.

Infinite penalties at zero step

For NormL1(Inf, w), the γ = 0 endpoint is lim_{γ→0+} prox_{γf}(x) with the function f held fixed. That function is the indicator of {0} in each coordinate with w[i] > 0 (an infinite w[i] included) and is zero in each coordinate with w[i] = 0, so the limit is the projection onto the closure of its domain: positive-weight coordinates become exactly +0, even for NaN or ±Inf inputs, and zero-weight coordinates are returned as soft thresholding by a zero threshold returns them (NaN and ±Inf unchanged). Unweighted NormL1(Inf) therefore maps every coordinate to +0. The order of limits matters: for a fixed finite level, shrink(x, γλ) → x as γ → 0+, but NormL1(Inf) is already the constraint at every positive step, so the result is not computed as shrink(x, 0⋅Inf). Among the NormL1 parameters, this rule is specific to the infinite overall level. An infinite coordinate weight at a finite level keeps the narrower #853 rule above (finite inputs fixed; non-finite inputs may give NaN), and finite factors whose product overflows are never treated as an infinite level (the finite-threshold limitation above). For finite levels and finite weights, γ = 0 keeps the identity. A finite positive Scaled factor passes the zero step through, so 2 * NormL1(Inf) projects as well; an infinite factor at a zero step forms the step Inf⋅0 = NaN in the wrapper before NormL1 sees it, and follows the wrapper's existing step arithmetic. ElasticNet follows this rule for an infinite λ1, and implements the same zero-step projection for an infinite ridge level λ2, the indicator of {0} in every coordinate. GroupNormL2 applies the same reading at γ = 0 to an infinite level (groups with a positive weight become +0) and to an infinite group weight, and NormL2 and NormLinf to an infinite level; no other function is claimed to implement a zero-step projection rule.

The endpoint history records the design decisions and performance evidence.

Signed zeros do not activate absent coordinates; explicit active signed zeros can be retained in storage. Symmetric-iterate isequal distinguishes stored negative zero from absent positive zero; == does not. dropzeros! removes either signed zero and preserves NaN/Inf.

Sparse product semantics

The specialized products in the operation table ignore zero iterate coefficients, stored or absent. No term is formed even if the other operand at that coordinate is NaN/Inf. A nonzero NaN/Inf coefficient contributes ordinarily. A zero in a dense factor remains an IEEE zero. A coordinate view uses ordinary dense-vector semantics instead.

using ProximalBase, LinearAlgebra
x = SparseIterate(2)
x[1] = 2
activate!(x,2)
v = [3.0,Inf]
@assert dot(v,x) == 6
@assert isnan(dot(v,coordinates(x)))
dropzeros!(x)
@assert dot(v,x) == 6
dot(v,x)
6.0

The LinearFunction value at a matrix SparseIterate follows the same rule, as its own computation and not through dot(c, x): a position that is not stored, or is stored as +0 or -0, contributes nothing and c is not read there, so a NaN or ±Inf coefficient at it does not reach the value, while a nonzero entry keeps ordinary arithmetic. For a dense c that is not a Diagonal, f(Matrix(x)) takes the dense IEEE dot and gives NaN for such a coefficient.

using ProximalBase, LinearAlgebra
x = SparseIterate(2, 2)
x[1, 1] = 2
activate!(x, 4)                    # the entry (2, 2) is stored as a zero
c = [1.0 NaN; Inf 1.0]

@assert f(x) == 2.25
@assert isnan(f(Matrix(x)))

Five-argument products with β=0 overwrite the destination without reading its old numerical entries; α=0 scales/clears output without reading right-operand values, after required type/shape/alias checks. Finite summation can depend on activation order; compaction can therefore change final rounding.

The direct A*X*B kernels for matching Float32/Float64 Symmetric-strided factors and matrix iterate X recover the range of individual finite three-factor terms. They promise accuracy within one neighboring floating value for a normal term, or one spacing for a subnormal term, not correct rounding. A non-finite sum is recomputed in scaled units only when all contributing factors are finite; true NaN/Inf data keep ordinary IEEE outcomes. Tiny terms can be rounded away beside large ones. Other mixed/generic product routes do not inherit this specific guarantee.

Validation, aliasing and evidence

Predictable type/shape/parameter errors precede built-in oracle output writes. A read, conversion or numerical failure can leave output changed. Storage state copies and matrix imports have distinct guarantees documented in views and aliasing. Parameter arrays are not made immutable or copied by validation. Call reset_cache! after same-shape cached data changes.
