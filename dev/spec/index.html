How to read the numerical contracts

The order of authority is current source and tests, numerical contracts, user and learning guides, then design history. If two disagree, report the disagreement as an issue. A documentation migration preserves the original wording and does not decide a new numerical policy or change an implementation.

Shared rules

Start with Array and precision conventions for arrays, precision, output ownership and aliases, and the Numerical contract for range recovery, non-finite values, sparse products and rules shared by several families.

Each family page is an entry point to its own rules and to these shared owners. The API reference continues to own signatures and docstrings. Brief safety reminders may repeat; detailed rules link to their owner.

Status vocabulary

Clause status must follow an explicit statement in the owning text and its evidence. An implementer must not promote a statement to a guarantee because the current implementation happens to produce that result.

StatusMeaning
guaranteedA promised behavior that must hold and needs test evidence; changing that promise is a breaking change
characterizedCurrent behavior recorded so a change is noticed, without promising it
limitationA known gap linked to an issue; do not fix it during a documentation change
preconditionA caller obligation, unchecked unless the statement explicitly says otherwise
non-guaranteeBehavior explicitly not promised
unclassifiedThe source text does not establish a status; an owner decision is required

The pilot retains the existing prose and endpoint table. It does not silently assign a status to every sentence. Clause conversion follows the review of that mechanical move.

Clause identifiers and ownership

After conversion, each clause uses a permanent identifier of the form family.operation.case, with lowercase words and hyphens within each part. An identifier is not reused or renumbered. A withdrawn clause keeps its identifier and a withdrawn marker. Short letter-and-number rule labels are not introduced into source comments.

Each clause has one owning section. Other pages link to it. Routine pages explain computations and cite the owning clauses; they do not add guarantees. The writing rules and change process govern preservation and review.

Family-page schema

Every family page uses these headings in this order:

Use stable explicit IDs spec-<family>-<section> on all fourteen headings. The suffixes, in order, are identity, definition, traits, arguments, preconditions, results, ordinary, range, endpoints, failures, limitations, elsewhere, evidence and history. Preserve an existing explicit ID, such as scad-endpoints, when applying this convention to a published page.

  1. Identity.
  2. Definition and domain.
  3. Traits.
  4. Supported arguments.
  5. Preconditions.
  6. Results.
  7. Ordinary-path clauses.
  8. Range clauses.
  9. Endpoint clauses.
  10. Failure behavior.
  11. Limitations and non-guarantees.
  12. Clauses owned elsewhere.
  13. Evidence.
  14. History.

During a verbatim migration, a section can link to an existing owner instead of duplicating a statement. Converting text into clauses is a separate, independently reviewed change. Ambiguous status or conflicting statements go to the migration's open questions for an owner decision.
