# What other libraries do well

Twelve scientific-computing manuals and the Diátaxis framework were read on
2026-11-25 for specific design choices that ProximalBase could adopt. The pages
were fetched as text: images, icons and narrow-screen behavior of the external
sites were not observed. This file keeps the conclusions; the URLs are the
pages actually opened.

## The choices worth adopting

Each entry names the source, what it does and how it maps to ProximalBase.
Cost: S is under half a day, M is one to three days.

1. **A runnable example on the front page, then a REPL-style quick start.** (S)
   [ProximalOperators.jl](https://juliafirstorder.github.io/ProximalOperators.jl/stable/)
   puts a four-step "Quick introduction" on its home page: construct `NormL1(3.5)`,
   evaluate it, call `prox`, then `prox!` into a preallocated array.
   [CVXPY](https://www.cvxpy.org/) shows a ten-line problem near the top of its home page.
   ProximalBase's home page has an example, but it follows a paragraph on convexity
   and proximal operators, and the first install command is on the second page.
   → [Home](prototypes/index.md) and [quick start](prototypes/quickstart.md) prototypes.

2. **Capability tables with check marks, split by the reader's filter, short cells.** (M)
   SciPy's [local minimizer table](https://docs.scipy.org/doc/scipy/tutorial/optimize.html)
   has five columns of ✓ next to the solver name ("Bounds", "Uses Gradient", "Utilizes Sparsity"), one
   instruction sentence above ("Find a solver that meets your requirements using
   the table below") and one legend line ("(✓) = depending on …").
   [Convex.jl](https://jump.dev/Convex.jl/stable/manual/operations/) splits its
   operations into one table per cone class with five columns and two notes codes
   defined once. [PETSc](https://petsc.org/release/overview/linear_solve_table/)
   splits its solver tables by kind and puts conditions inline ("only for bs = 2,3,4,5"),
   but leaves blank cells undefined, a weakness to avoid.
   → [Capability tables](compatibility-tables.md): two tables per role (operations,
   inputs) with at most eight short columns, every cell symbol defined.

3. **A blunt "is this the right package?" statement.** (S)
   JuMP's [Should you use JuMP?](https://jump.dev/JuMP.jl/stable/should_i_use/) lists
   when to use it and, in separate short sections, when not to, each with an
   alternative. [ProximalAlgorithms](https://juliafirstorder.github.io/ProximalAlgorithms.jl/stable/guide/getting_started/)
   states in a note that it "does not offer a modeling language".
   → A "ProximalBase and ProximalSolvers" table on the home page. It is too small for
   a page of its own.

4. **Sidebar order equals reading order, with project material last.** (S)
   [Ceres Solver](https://ceres-solver.github.io/ceres-solver/) orders its sidebar
   Why → Installation → Tutorial → Modeling → Solving → … → Contributing → Version
   history. [JuMP](https://jump.dev/JuMP.jl/stable/) explains its sections in a
   short paragraph each on the home page.
   → [Proposed navigation](architecture.md).

5. **One fixed order for every function entry.** (S to define)
   [PyTorch](https://docs.pytorch.org/docs/2.15/generated/torch.nn.Softplus.html):
   signature, summary, formula, explanation, parameters, shape, example.
   [scikit-learn's user guide](https://scikit-learn.org/stable/modules/linear_model.html)
   opens each estimator with *when to use it* (elastic net "is likely to pick both"
   correlated features where the lasso picks one), then the objective, then a short example.
   ProximalOperators lists signature, formula and parameter constraints; a few entries
   mention operations (`IndAffine` describes its `prox!`), but there is no systematic table
   of the operations each function supports, the gap ProximalBase can fill.
   → The [function entry template](editorial-principles.md#function-entries) and
   four [prototypes](prototypes/functions/).

6. **Shared figures of penalty and constraint shapes.** (S)
   scikit-learn's [SGD page](https://scikit-learn.org/stable/modules/sgd.html) has one
   figure of penalty contours and one of losses. Ceres has one figure of the shapes of
   its common built-in losses ([modeling page](https://ceres-solver.github.io/ceres-solver/nnls_modeling.html))
   and gives each of them little more than a formula.
   → [Five prototype figures](prototypes/visualizations.md), generated by the same
   standard-library approach as `docs/generate_learn_figures.py`.

7. **Decision rules as a two-column table, not a flowchart.** (S)
   scikit-learn's Ridge section has a "Solver | Condition" table. Its
   [estimator flowchart](https://scikit-learn.org/stable/machine_learning_map.html)
   calls itself "a rough guide" and is an interactive inline SVG, which goes stale with
   the library and is harder to scan than a table.
   → "If your model needs … use …" rows at the top of the [catalog](prototypes/catalog.md).

8. **A pitfalls page in the style of JAX's "sharp bits".** (M)
   [JAX](https://docs.jax.dev/en/latest/notebooks/Common_Gotchas_in_JAX.html) gives
   each pitfall a heading, the expected behavior, code, the surprising output, the
   reason and the fix.
   → Candidate material: `LeastSquaresLoss` is ½‖y−Xβ‖² without 1/n;
   `value_and_prox!` is documented to return the value at the *output*; a gradient output must not
   share memory with its input; for a finite α > 0, the proximal step of `Scaled(f, α)`
   at step γ is, in exact arithmetic, that of `f` at step αγ, where `Scaled` supports the
   operation; `NormL0`, and `MCP` at a step γ ≥ a, return zero on an exact tie,
   while `SCAD` picks the minimizer of smaller magnitude;
   `SparseIterate` is a working set, not compressed storage. The proposal puts these in
   the "Good to know" lists of the function entries and defers a separate page
   ([decision 7](README.md#decisions-for-the-maintainer)).

9. **Examples that change one argument at a time.** (M)
   Ceres' [tutorial](https://ceres-solver.github.io/ceres-solver/nnls_tutorial.html)
   turns curve fitting into robust curve fitting by changing one argument (`CauchyLoss`).
   → A lasso → MCP → `SparseIterate` progression in the existing Literate pipeline.

10. **Reference stays neutral; rationale is linked, not inlined.** (S)
    Diátaxis ([reference and explanation](https://diataxis.fr/reference-explanation/))
    notes that explanatory material sprinkled into reference "is bad for the
    reference, interrupted and obscured by digressions". CVXPY centralizes
    curvature and sign in its [user-guide atom tables](https://www.cvxpy.org/tutorial/functions/index.html)
    instead of relying on its API docstrings for them.
    → Capability facts live in the capability tables and function entries;
    docstrings link to them instead of repeating a support list.

11. **Admonitions with fixed meanings.** (S)
    JuMP's [manual](https://jump.dev/JuMP.jl/stable/manual/variables/) uses warning for
    pitfalls, tip for advice, info for rationale.
    → Added to the [editorial principles](editorial-principles.md).

12. **Shared operation vocabulary with the solver package.** (S)
    ProximalAlgorithms' [algorithm tables](https://juliafirstorder.github.io/ProximalAlgorithms.jl/stable/guide/implemented_algorithms/)
    have an "Oracle" column (`∇f`, `prox_{γg}`).
    → Use the operation names as column headers in ProximalBase and link to
    ProximalSolvers' supported-problems page. Using the same names in ProximalSolvers'
    documentation would be a suggestion for that package, outside this series.

## Choices that do not fit ProximalBase

- **A generated page per symbol** (PyTorch `torch.nn.<Name>`, SciPy per-function pages).
  Thirty functions and one maintainer: per-symbol pages multiply navigation and
  maintenance and split the comparison a reader wants to make. Function entries
  are grouped by role instead (see [architecture](architecture.md#function-entries-grouped-pages-not-one-page-per-function)).
- **Example galleries** (scikit-learn's sphinx-gallery). They need Sphinx tooling. The
  nine Literate examples are the right size.
- **Flowcharts** for choosing. They go stale and are harder to scan and maintain than a table; use a decision table.
- **Icon legends** (CVXPY's curvature icons). They are images that search cannot find and
  screen readers handle poorly; use ✓ and short text.
- **A capability table generated from method tables or traits.** CVXPY derives its
  table from atom attributes, but in ProximalBase a method, trait or fallback is not
  proof of support (#1212 G4). Keep the table hand-written, cite the evidence for each
  cell in the developer coverage matrix, and review it with each family change.
- **Large tutorial volumes, numbered user-guide chapters and versioned API trees**
  (JuMP's tutorials, scikit-learn's chapters, PyTorch's version paths). These answer
  problems of scale ProximalBase does not have.
- **A home page with an install command but no worked example** (Optim.jl,
  ProximalAlgorithms). A runnable example on Home is what this proposal adds.

## Diátaxis: a review tool, not a folder layout

[Diátaxis](https://diataxis.fr/) distinguishes tutorials (learning by doing),
how-to guides (doing a task), reference (looking something up) and explanation
(understanding). Its own guidance ([how to use Diátaxis](https://diataxis.fr/how-to-use-diataxis/))
says that "the structure it proposes is not intended to be a plan", that getting
started "does not require you to think about dividing up your documentation into
four sections", and that it "is designed to guide small steps". The top-level
structure should emerge from improving individual pages.

Applied here:

| Existing ProximalBase content | Kind | What to watch |
|:--|:--|:--|
| New quick start; `getting_started.md`; `proximal_gradient.md`; `coordinate_descent.md`; `learn/proximal_exercises.md` | Tutorial | Every step must run and produce a visible result; keep "which function should I choose" branches out |
| Literate examples | Tutorial or how-to | Title each by its goal |
| Catalog decision rows, `extending.md`, `restrict.md`, `calculus.md` | How-to | Title by the task; practical before complete |
| Function entries, capability tables, API pages, family guarantee pages | Reference | Neutral and uniform; no history or rationale |
| `numerical_usage.md`, `numerics.md`, `function_objects.md`, `learn/floating_point.md`, glossary, `architecture.md` | Explanation | Do not let it absorb reference tables |
| `developer/`, `migration.md` | Contributor and project material | Outside the user journey; the same four kinds apply inside it |

The largest risk is the opposite of the usual one: the current family guide
pages (`smooth.md`, 6,300 words; `group_penalty.md`, 6,800 words) are reference
pages that have absorbed explanation and edge-case detail. The redesign moves
detail to the guarantee pages and leaves the user entry short.

## Tables on narrow screens

Documenter 1.20 makes tables scroll horizontally inside the content column
(`.content table { display: block; overflow-x: auto }` in its theme source). It does
not wrap rows into cards or pin the first column. A table is usable on a phone
when it has at most about seven narrow columns with short cells. The current
catalog and selection tables, whose cells hold several sentences, are not; see the
[audit](audit.md#narrow-screens). Cards would need custom HTML and CSS, which is
not worth it for about 30 rows.
