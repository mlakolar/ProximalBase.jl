# Numerical contract for 0.6: design record

The numerical contract is published in `docs/src/numerics.md`. This folder
keeps the record of how it was decided. It is outside `docs/src`, so
Documenter does not build it. Historical decision and audit records retain
the storage names used at their pinned commits. The current public names are
`BlockIterate`, `blockview` and `blockindices`; those records do not define
compatibility aliases. The generated coverage map reflects the current tests.

| file | content |
|:---|:---|
| `decisions.md` | the 47 decisions, each opening with the maintainer's approved **Decided** line (2026-11-01), followed by its background, options, precedent in other packages, first recommendation and revisions, kept as history |
| `impact-on-open-issues.md` | the open issues and pull requests the decisions affect, screened on 2026-10-31; a work list until the tracker #366 takes it over |
| `bench-q1-threshold.jl` | measurement behind decision 3: soft thresholding with a rounded, a per-entry `Float64`, and a two-word threshold |
| `coverage.md` | the reconciliation table of the conformance suite (`test/conformance/`, extended tier), generated by `scripts/conformance_map.jl` from the reports of one run of the suite (`scripts/conformance_run.jl`): for each family, oracle, element types and backend, the problem after conversion, the promised result and the status today (passes, broken with its change group of #366, or not covered). Regenerate it with `julia scripts/conformance_run.jl <empty report dir> --out docs/design/numerical-contract/coverage.md`, which runs the suite into the empty directory under one run id and rejects stale, partial or foreign report files; `--check` diffs it. The CI test job writes the reports in thorough and full runs (pushes to master, tags, the nightly run and manual runs of those tiers, or a pull request whose tier is thorough or full, for example with the label `test:thorough`). A full run writes all 14 report files and uploads them as the artifact `conformance-reports-<version>-<os>-<arch>-<attempt>`; a thorough run does not run `conformance/gpu_arrays` (a full-tier file) unless its changed paths (`test/conformance/`, the report scripts, this map) or the label `test:gpu` add it, so its reports may lack `gpu_arrays.jsonl` and are uploaded as `conformance-reports-partial-<version>-<os>-<arch>-<attempt>`, a partial inventory that is never the base of a regenerated map (an upload counts only when GitHub returns an artifact id, and is otherwise retried once; only the upload of the job that checks the map is required, which is Julia lts on Linux when the run has it and otherwise Julia 1 on Linux, so an artifact of another job can be missing, with a warning in that job); if the test step failed, the artifact is named `diagnostic-conformance-reports-...` (`diagnostic-conformance-reports-partial-...` below full) and is never a baseline (the rows record passes and known breaks, not unexpected failures, so a matching map does not show that the tests passed). That job also checks the committed map with `--check --tier <tier> --extra <focus files>` (options of `conformance_map.jl`, not of the runner), which ignores the run provenance lines (run heading, SHA, run id, harness revision, Julia line) and compares everything else. With every report file present and no `--tier`, or `--tier thorough` or `full`, this is the complete check (`--tier quick` and `--tier standard` are rejected before the report files are examined). When only an omittable report (`gpu_arrays`) is absent at thorough, the check compares a partial inventory (it says so): the rows of the other families, the case-id and required-row lines and all other lines must match the committed map, while the rows of the absent family, the executed broken-row counts and the line listing the missing report files are not compared; any other missing or unexpected report file, and `gpu_arrays` missing at full or without `--tier`, fails, and the recognized partial inventory (`--tier thorough`) never writes a map. The harness writes reports as rows are emitted when `CONFORMANCE_REPORT` and `CONFORMANCE_RUN_ID` are both nonempty, and CI gives `CONFORMANCE_REPORT` a value only for thorough and full runs, so CI's quick and standard runs write none; a pull request that changes conformance rows gets the thorough tier from its changed paths (`test/conformance/`, this map) or needs the label `test:thorough`. To regenerate from a CI artifact, use the `conformance-reports-lts-ubuntu-latest-x64-<attempt>` artifact (not the `partial` one) of a full run that has Julia lts on Linux and whose test step succeeded, into a fresh directory, and copy the map only when generation succeeds: `gh run download <run id> -n <artifact name> -D <fresh dir>`, then `julia scripts/conformance_map.jl <fresh dir> --run-id ci-<run id>-<attempt>-lts-ubuntu-latest --out <fresh dir>/candidate.md && cp <fresh dir>/candidate.md docs/design/numerical-contract/coverage.md` (the generator writes its output before it reports missing rows, so never point `--out` at the tracked file) |
| `bench-d6-quadratic.jl` | measurement behind decision 6: a `Float32` quadratic at a `Float64` argument |

## The full record

The design was discussed on
[pull request #385](https://github.com/mlakolar/ProximalBase.jl/pull/385),
where every exchange is a comment. The drafts and reviews named in
`decisions.md` were removed from this folder when the contract was published.
They are in the pull request's history at commit
[`850e2bd2`](https://github.com/mlakolar/ProximalBase.jl/tree/850e2bd2/docs/design/numerical-contract):

- `01`: ChatGPT's reader's edition (Draft 2);
- `02`, `03`: Claude's review of it, and Draft 3;
- `04`: ChatGPT's comparison with #366;
- `06`, `08`, `11`, `13`, `15`: Drafts 4–8;
- `07`, `09`, `12`, `14`, `16`: ChatGPT's reviews of Drafts 4–8, the last its sign-off;
- `10`: the impact on open issues, kept here as `impact-on-open-issues.md`.

## How the contract was settled

1. ChatGPT drafted a reader's edition.
2. Claude reviewed it against the code and #366 and wrote Draft 3, with rule
   identifiers and statuses.
3. Five rounds followed, each a ChatGPT review and a Claude revision. Every
   numerical claim was run on the package, and the revision recorded the
   commit it was checked at.
4. The maintainer approved all 47 decisions on 2026-11-01.
5. Implementation follows in separate pull requests, tracked in #366, starting
   with a reconciliation table: for each oracle, the problem after conversion,
   the promised result, the acceptance case, and its status.
