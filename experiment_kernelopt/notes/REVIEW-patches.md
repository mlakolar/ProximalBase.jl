# Review of performance patches

Reviewed against `50db4b1ef376cbe01831c3dd019b6be0027db0b6`; A2 was applied after A. References below are to master source or physical lines of the supplied diffs. Verdicts apply to the patches as submitted, including the strict >5% slowdown rule.

Probes and logs are in `.codex-probes/`. Julia 1.13.4 and 1.10.13 were exercised. Current-version changed test files passed; the added numerical tests also passed separately on 1.10, as did B's array-step tests and D's norm/group oracle tests. C2 passed the existing numerical-kernel, NormL2 and ridge tests on current Julia, and NormL2/ridge tests on 1.10. The full numerical-kernel file on 1.10 stops at the **same inherited failure on unchanged master**: `test/numerical_kernels.jl:735` allocates 16 bytes where it asserts zero. That failure is not attributed to a patch.

Performance evidence uses warmed, allocation-free calls, alternating batches and BenchmarkTools confirmation. This is a hybrid CPU: affinity 0 selects a performance core, affinity 12 an efficiency core. Small-call results are sensitive to code layout; the findings below identify reproducible callers rather than extrapolating a universal percentage. Reproduction scripts are `.codex-probes/bench-focused.jl` and `.codex-probes/benchmarktools.jl`; their pinned-core logs contain the repetitions. For example:

## A

**APPROVE WITH CHANGES**

- **MINOR — Correct the test and hardware claims in the comment.** `review/patch-A.diff:9` says each select is one hardware instruction, including Float16, and line 14 says the tests compare every Float16 pair. Instruction selection depends on architecture/type/compiler; the committed test samples thresholds every 97th bit pattern (`review/patch-A.diff:69`). Reword to “all Float16 values against sampled thresholds,” and qualify the instruction claim. A separate exhaustive reviewer probe did compare all 2^32 Float16 pairs and found no discrepancy, but that is not the added test.

- **NOTE — The numerical equivalence holds under ordinary IEEE round-to-nearest arithmetic.** The second operand of each select is always +0, so it cannot introduce a second-operand NaN-propagation difference. The relevant signed-zero difference is the first term at `v=-0, c=+0`; the other term is +0, and the final sum remains +0. Negative thresholds, overflowed additions/subtractions, infinities and NaNs introduce no further difference under the requested NaN equivalence. The exhaustive Float16 probe and Float32/Float64 edge/random tests agreed. The existing promotion method remains; BigFloat retains the generic method, including directed rounding. No dispatch regression or new ambiguity was found. No numerical fix is needed.

- **NOTE — Scope and tests are appropriate apart from the wording.** The added tests call the actual `shrink`, compare against an independent spelling of master's expression, and check mixed arguments and BigFloat dispatch/rounding (`review/patch-A.diff:118`). They would detect arithmetic changes on their sampled domain. The new IEEE overload and two private inline helpers add modest specialization work, without extra array scans, allocations or recovery machinery. A more-specific method can require recompilation of previously compiled intersecting calls when loaded into a live session; this is a package-owned function, with no type piracy. Ordinary proximal throughput improved in the measured cases; no reproducible >5% regression was established. Missing coverage is public array-level integration/aliasing, rather than a hole in the scalar proof.

## A2

**REJECT**

- **BLOCKER — It slows an existing ordinary path relative to its actual parent, A.** At `review/patch-A2.diff:10`, every normal-threshold L1 operation switches kernels. With Float64 `x=fill(1.1,1024)`, `w=fill(0.75,1024)`, `NormL1(0.3,w)` and scalar step `0.5`, pinned performance-core BenchmarkTools runs measured approximately **105–107 ns with A versus 114 ns with A2**, a repeated **6.6–9.0% slowdown**. Alternating batches agreed. This is an ordinary homogeneous call. Comparing A2 only with master conceals the regression. Small calls also regress. Smallest compliant fix: retain A's kernel; do not switch the shared scalar path to this alternative.

- **MAJOR — This introduces a second mathematical implementation of soft thresholding.** `review/patch-A2.diff:30` implements clipping/subtraction alongside the existing sum-of-selects implementation. Correctness now depends on choosing the right domain at each call site. That conflicts with the explicit no-duplicated-mathematical-implementations rule, independently of the timing failure. Retain the canonical `shrink` implementation rather than maintaining both formulas.

- **MAJOR — No regression tests are added for the new helper or its integration.** A's tests still exercise `shrink`, not `_shrink_nonneg`. `review/st_clampz.jl:5` tests a separate local implementation and is not included by the test runner. It would continue passing if the package helper or its dispatch were broken. If reconsidered, tests must call the actual helper and public prox routes, covering signed zeros, NaN/Inf thresholds and inputs, underflow/overflow thresholds, integer/mixed parameters, fallback types and exact in-place calls.

- **NOTE — The stated scalar identity is sound; the call-site precondition is conditional.** The exhaustive reviewer Float16 probe found no difference for any threshold satisfying `!(c < 0)`. For finite nonnegative c, clipping selects v inside the interval and the appropriate endpoint outside it; +0 repairs the zero sign. NaN propagation and infinite endpoints agree with `shrink`. BigFloat falls back unchanged, and mixed/integer arguments retain promotion. However, construction does not permanently establish nonnegative weights: `NormL1` stores its weight array directly (`src/functions/norml1.jl:43`), and oracle validation checks length, not signs (`src/utils.jl:55`). Reproducer: `w=[1.0]; f=NormL1(1.0,w); w[1]=-1.0; prox(f,[0.0],1.0)` changes from `[0.0]` to `[1.0]`. This mutation leaves the valid parameter domain, so it is **not** a supported-input correctness blocker. Do not claim construction makes it impossible, and do not add a hot-path validation scan to repair it.

- **MINOR — Shorten and correct the explanatory comment.** `review/patch-A2.diff:24` omits the threshold negation from the operation count. At a NaN v and positive finite c, the second select returns `-c`, not c; v propagates its NaN through the subtraction. Explain those facts directly instead of promising a universal instruction count.

## B

**REJECT**

- **BLOCKER — The prepass taxes paths it does not accelerate, and short all-normal calls also regress.** `review/patch-B.diff:19` scans every step before falling back to master's entire loop. With Float64 `x=fill(1.1,7)`, `NormL1(0.3)` and `γ=fill(0.5,7)`, all products are normal, yet pinned performance-core BenchmarkTools runs measured **7.68–7.71 ns → 8.11–8.12 ns**, repeatedly **+5.3–5.6%**. On the efficiency core this case regressed much more. One zero step also forces the prepass plus generic loop: ordinary neighboring coordinates receive no benefit; alternating-batch results at larger sizes showed additional >5% regressions. Zero levels likewise buy only a failed scan. Smallest fix for short arrays is a measured lower-size cutoff; that alone does not fix the fallback tax. Do not land the unconditional prepass without a design that meets the fallback performance requirement.

- **NOTE — The specialized signature, working precision and `invoke` are correct.** `review/patch-B.diff:14` reaches same-type Float32/Float64 Arrays, with absent or same-type Array weights. Views, offset/custom arrays, differently typed weights/data/output/steps, Float16 and integer arrays retain the generic route, including their existing indexing/error behavior. For Float32 data and Float64 **or Int** λ0, `_working_type` is Float64; `_steps_normal` uses that type, and `_threshold_product(T,...)` still performs the same promoted multiplications followed by conversion to T (`src/numerical_kernels.jl:82`). A BigFloat level yields BigFloat R and correctly falls back. The `invoke` signature at diff line 21 selects the generic method at `src/functions/separable.jl:143`; it does not recurse or create an ambiguity. Broad differential probes on both Julia versions found no mismatch.

- **NOTE — Validation and aliasing preserve behavior, with repeated checks on fallback.** The successful route performs the same `_checkwrite` and step-length validation as the generic loop. Public callers still validate real arguments (`src/array_steps.jl:32`, `src/symmetric_parameters.jl:117`). Failed range tests repeat `_checkwrite` and `_checkparam` inside the invoked generic method. No validation is skipped. Empty arrays pass vacuously and perform no writes; same-length step arrays of a different shape retain linear indexing. Exact `y===x`, `y===γ`, and their combination have no cross-iteration dependence: each entry's operands are loaded before its store, and the scan finishes before writing. Plain `@simd` therefore does not authorize a wrong result for those aliases. Derived overlapping storage remains outside the documented guarantee. No new allocation was found.

- **MINOR — Keep comments conditional on actual compiler behavior.** `review/patch-B.diff:9` describes scalar-loop hoisting and vectorization as universal facts. Qualify them by the measured configurations. In the bit-order explanation at line 45, explicitly say **positive** Inf/NaN patterns exceed floatmax; negative patterns fail the lower bound. The sign-aware min/max range test itself is correct, including signed zeros and both NaN signs.

- **NOTE — Numerical tests cover the new route well, but cannot enforce the performance claim.** The direct range-test tests exercise `_steps_normal`; public tests actually dispatch to the specialization and compare against `prox_block`, including in-place output, output-as-steps, exceptional steps, mixed/Int levels, matrices and views. They pass. Add performance coverage for short arrays and failed scans, plus BigFloat-level fallback, resized weight arrays and malformed output shapes with before-write assertions. The output tests alone would still pass if the specialized loop were never selected. The new overload/loop adds specialization and possible recompilation of intersecting generic calls, but no detected ambiguity; reusing `_threshold_product` avoids duplicating its recovery mathematics.

## C

**REJECT**

- **BLOCKER — The blanket “up to 2^17” switch includes a losing ordinary small-array path.** `review/patch-C.diff:16` sends singleton arrays through a zero-initialized SIMD reduction instead of Base's singleton reduction. In pinned performance-core, warmed noinline value-call batches, `NormL1(0.3)([1.1])` repeatedly measured **2.74–2.75 ns → 2.94–2.95 ns**, **+7.1–7.2%**. These are small absolute times but the stated rule supplies no small-call exemption. Direct-call timings vary with layout, so this is a finding about that reproducible ordinary caller, not every caller. Smallest fix: retain Base's path for the losing small sizes and remeasure the cutoff; the new loop is substantially faster at useful intermediate sizes.

- **NOTE — The summation claim is numerically reasonable, but the error growth changes substantially.** For normal finite nonnegative terms without intermediate overflow, let `u=eps(Float32)/2`. A conservative one-loop bound is `γ_n = n*u/(1-n*u)`: at `n=2^17`, **0.007874**, or about **0.7874%** relative error, before the final multiplication. SIMD lanes usually reduce the effective chain length, but their count is not a portable accuracy guarantee. Fully pairwise summation gives `γ_17 ≈ 1.01e-6`; Julia's actual pairwise reduction has sequential SIMD leaf blocks (see `src/numerical_kernels.jl:645`), so a conservative 1024-entry-leaf bound is roughly `γ_1031 ≈ 6.15e-5`. The distinction is linear growth in a long lane versus bounded leaves plus logarithmic tree depth. As a concrete rounding example on current Julia, `NormL1(1f0)(fill(0.1f0,2^17))` changes from `13107.195f0` to `13107.705f0`, about 323 eps from the exact value.

- **NOTE — No stronger general L1 summation contract was found.** `docs/src/numerics.md:97` states a `4n eps` bound for **recovered** values, not a general few-eps guarantee for every ordinary reduction; lines 142–147 disclaim correctly rounded reductions and fixed arithmetic order. Applying the new tests' `4n eps` tolerance to ordinary sums permits **6.25%** at the cutoff. Existing norm test helpers use tighter tolerances on particular fixtures, not a universal summation theorem. The least-squares pairwise/accuracy statements (`docs/src/smooth.md:119`, `test/leastsquares_predictor.jl:976`) concern another route; the million-entry pairwise case remains unchanged. No supported exceptional-value contradiction was found: the existing level checks and overflow fallback remain in place.

- **NOTE — Dispatch limits both the benefit and test coverage.** The public caller is still restricted to `DenseArray{<:AbstractFloat}` (`src/functions/norml1.jl:93`). Ordinary views are StridedArrays but are not DenseArrays; they reach the generic separable value route and never call this new helper. BigFloat/Float16 DenseArrays use its generic `sum` fallback; integer and offset/custom arrays, weighted functions, sparse/block iterates and prox/fused-value routes are unchanged. Above the cutoff, there is an added length test before the original reduction. No allocation or ambiguity was found.

- **MINOR — Tests are useful but miss range recovery and the performance rejection.** `review/patch-C.diff:47` tests the actual Array loop, independent BigFloat references, remainder lengths, the cutoff, matrices, endpoint classes and allocation. Those checks can catch numerical failures in their domain. The view checks at lines 79–80 exercise the unchanged generic route. Add finite sum/product overflow recovered by a small level, subnormal sums/levels, wide levels outside T's range, and explicit fallback-type tests. State clearly that the loose ordinary-sum tolerance is being chosen here; qualify “faster ... in cache” at diff line 13 because singleton cache-resident arrays disprove the unqualified version.

## C2

**REJECT**

- **BLOCKER — Reusing the helper also imports its small-array cost.** `review/patch-C2.diff:10` changes the uncentered SqrNormL2 value at every strided Float32/Float64 length below the upper cutoff. For `SqrNormL2(0.3f0)(Float32[1.1])`, pinned performance-core BenchmarkTools repetitions measured **2.756–2.757 ns → 2.952 ns**, consistently **+7.1%**. The old singleton square reduction does not need the new zero-initialized reduction's work. Retain `_sumabs2` at losing small sizes at these call sites, and verify the crossover. Changing the shared helper globally would also change least-squares paths outside this patch's intended scope.

- **NOTE — Numerical compatibility is plausible; “same kind of rounding” includes hundreds of eps.** The bounds discussed for C apply to the square sum, with another rounding for each square. NormL2 roughly halves the sum's relative error through the square root, then adds square-root/scaling rounding; SqrNormL2 retains the sum's error order. On current Julia, `x=fill(1.1f0,2^17)` with level `1f0` gives NormL2 **398.2425f0 → 398.2378f0** (about 100 eps error) and SqrNormL2 **79298.55f0 → 79296.664f0** (about 201 eps error). This is within a linear-in-n bound, not a few-eps ordinary-value claim. `test/norml2.jl:26` and line 38 use 8/4-eps checks for their fixtures; no general pairwise or few-eps promise for all ordinary arrays was found. The few-eps *overflow-recovery* promises in the NormL2 docstring and `docs/src/numerics.md:129` are retained: `_l2_ordinary` still forces recovery near floatmax (`src/numerical_kernels.jl:1013`). SqrNormL2 retains its exceptional trigger and scaled recomputation; its `λ*s/2` numerator overflow also causes recovery (`src/numerical_kernels.jl:620`).

- **NOTE — The implementation is minimal and keeps other representations intact.** The existing helper already handles strided matrices/views and falls back to `_sumabs2` for other arrays, Float16, BigFloat and integer inputs. Sparse/symmetric/block overrides remain reachable, including stored-entry complexity. Offset/custom arrays keep their original generic reduction. Centered SqrNormL2 still uses `_sumabs2_diff`; gradients/proximal maps are unchanged, while their returned value can inherit the allowed sum-order difference. There are no new methods, recovery algorithms or mathematical copies. Above the cutoff only dispatch/length-test overhead is added; no large-array >5% regression or new allocation was established.

- **MAJOR — No tests are added.** Existing suites pass but do not test these newly selected norm paths around `2^17`. Add independent references at cutoff-minus/at/plus, constants and mixed magnitudes, strided views/matrices, empty/singleton inputs, NaN/Inf/zero/infinite levels, finite overflow/underflow recovery, and agreement of standalone/fused values at the appropriate stored point. Include integer/Float16/BigFloat and sparse fallbacks. Keep comparisons sensitive to the stated error bound rather than requiring identical bits.

- **MINOR — Update stale scope comments.** `src/numerical_kernels.jl:632`, retained by `review/patch-C2.diff:7`, still says `_square_value` uses `_sumabs2`. The comment at source line 645 calls the shared cutoff a least-squares-route limit; this patch extends its use. Update both without copying the implementation or silently changing the cutoff for unrelated callers.

## D

**REJECT**

- **BLOCKER — The failed guard adds an underflowing multiplication and a reproducible slowdown.** `review/patch-D.diff:10` computes `c*c` before retaining the original zero scan. Use `x=zeros(Float64,1000)`, 1000 singleton groups, unit Float64 weights, `GroupNormL2(floatmin(Float64),groups,w)` and step `1.0`. The threshold is positive and normal; both versions return exactly +0 and zero fused value. Pinned efficiency-core BenchmarkTools repetitions measured approximately **6.45 μs → 85.4 μs**. The performance core also regressed about **9.8–10.3%**. This guard never succeeds for that c, so it adds work to an already handled zero-group path. Smallest fix: avoid squaring c in the guard. A conservative sufficient comparison such as `c >= length(G)*sqrt(floatmin(T)/eps(T))` can avoid that underflowing square (for nonempty groups it is stronger than the proposed square test); verify its rounding and timing before substituting it. No additional recovery machinery is warranted.

- **NOTE — The proposed zero decision is otherwise sound.** With `s==0`, every converted entry's square is at most `δ/2`, where `δ=nextfloat(0)`, so the exact converted norm squared is at most `n*δ/2`. The guard's scale is `n*floatmin(T)/eps(T) = n*δ/eps(T)^2`, many orders larger. Rounding `c*c` near the guard boundary cannot bridge that gap. If `c*c` underflows, the positive bound makes the guard fail; if it overflows, c is already vastly larger than the possible norm. For Float32/Float64 the bound remains finite for an Int-sized length; the Float16 exclusion is material because conversion of a large length to Float16 can make the bound Inf. Wider raw entries that narrow to these tiny T entries remain far below c. No numerical counterexample was found, including mixed output/input types.

- **NOTE — Return codes and fused values are preserved.** The new exit uses the same `T(_l2_zero!(y,G))` as the old zero-group exit (`src/numerical_kernels.jl:956`). The cold route also returns `_L2_ZERO` when the norm is below c. `_l2_fused_term` immediately returns zero for that code (`src/numerical_kernels.jl:1044`), correctly representing the stored all-+0 group; this does not substitute an unrounded norm for a fused value. Empty groups at the internal kernel, zero/infinite parameters, NaN/Inf data and nonzero normal square sums take their existing exits. Float16/BigFloat output types retain the old scan; public one-based-index checks still reject offset prox arguments before writing. No new allocation or method ambiguity was found, although the shared inline kernel grows for every caller.

- **MINOR — The tests are strong on correctness and silent on the failed-guard cost.** The added primitive tests (`review/patch-D.diff:189`) compare actual outputs **and codes** with the existing cold route, then independently check nonzero shrinkage against BigFloat. Public tests cover fused values, exact in-place calls, ranges/permuted groups, matrices, mixed precision, overflowing squares of thresholds and both sides of the guard boundary. They would catch an unconditional zeroing error. Add timings for zero groups with tiny normal thresholds and ordinary nonzero groups. The long source comment should distinguish the mathematical bound from overflow caused by converting the length to Float16, and explicitly acknowledge rounding of `c*c`; its core inequality is valid.
