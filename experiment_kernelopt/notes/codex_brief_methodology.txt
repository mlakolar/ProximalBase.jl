Context. This checkout is the Julia package ProximalBase.jl at master 50db4b1e plus a research directory `experiment_kernelopt/` that benchmarks ProximalBase's numerical kernels (soft thresholding / NormL1, Euclidean norm and group shrinkage / NormL2 and GroupNormL2, least squares) against (a) minimal standalone kernels in `experiment_kernelopt/kernels/kernels.jl`, (b) ProximalOperators.jl, LinearAlgebra and BLAS, and (c) patched ProximalBase source trees ("candidate trees"), on Julia 1.13.4 and 1.10.13, on a Slurm cluster. Conclusions drawn from it will be used to propose production changes under a policy that treats any reproducible slowdown above 5% on an existing ordinary hot path as disqualifying, so both false improvements and false regressions matter.

Files to review: experiment_kernelopt/bench/harness.jl (timing loop, calibration, output comparison), bench/suites.jl (the cases: what each implementation computes), bench/solvers.jl (solver-level loops), bench/run.jl (how source trees are loaded as modules and how the reference tree and its A/A control are chosen), bench/summarize.jl (statistics), kernels/kernels.jl, slurm/screen.sbatch and slurm/formal.sbatch (pinning, process structure), bench/numerics.jl (numerical behavior tables against BigFloat). Questions to answer, each with file:line evidence and, where you can, a concrete failure scenario or a small experiment:
1. Timing validity. Can the compiler hoist, elide or constant-fold any timed operation (pure kernels on unchanged inputs, results stored through a Ref, closures built by `thunk`/`thunkref`/`thunkscaled`)? Is `@noinline invoke_op` sufficient? Is the per-call overhead of the closure call identical across implementations of a case, and how large is it relative to the smallest kernels (a 2-entry group norm takes a few ns)? Does `calibrate` or the min-of-samples estimator bias comparisons between implementations with different evals counts?
2. Equal work. For each case family in suites.jl, do all implementations do the same mathematical work on the same data? Flag every place where an implementation does less or more (e.g. ProximalOperators' `prox!` also returns the function value; `thunkscaled` multiplies by λ outside the kernel; kernel variants that skip checks the library must make; matrix-column views versus index groups; Cholesky versus SVD setup placed inside or outside the timed region; `two_steps_thunk`; `first_prox_thunk*` argument orders). Say whether each difference is disclosed by the `level`/`note` fields or silently biases a ratio.
3. Shared state. Inputs and outputs are shared by all implementations of a case and operations are repeated on the same data: can state left by one implementation change the work of the next (outputs that are also inputs, cached factorizations keyed on γ in `CholLS` or in the libraries, the least-squares loss scratch, branch-predictor training on repeated identical data, subnormals)? Is anything in-place that should not be?
4. Order, placement and noise. The harness rotates and reverses the order of implementations each round and compiles the reference tree twice (A/A control `<ref>C`). formal.sbatch runs several fresh processes with rotated tree load orders. Is this enough to separate code-placement artifacts (known to reach 7–40% for identical code in this project) from real differences? What should the decision rule be when the A/A control itself deviates? Is one pinned core on an exclusive node, `--threads=1`, BLAS threads = 1 adequate; what about frequency scaling, the first-touch NUMA placement of the shared arrays, and transparent huge pages?
5. Statistics. summarize.jl reports the median of per-round paired ratios and its 10%/90% quantiles, pooling result directories. Is pooling across processes sound? What interval or test would you require before calling a ±5% difference real?
6. Correctness checks. harness.jl compares every implementation's output with the reference implementation and with an independent BigFloat reference under a per-case relative tolerance (`reldiff`). Are the tolerances and the scaling of `reldiff` (relative to the largest reference magnitude) able to hide a wrong implementation? Are the BigFloat references in suites.jl and numerics.jl truly independent of the code under test and correct (soft threshold, group shrinkage, least-squares prox normal equations)?
7. Kernel variants. In kernels/kernels.jl check each soft-threshold form (`st_*`) and the norm variants (`norm_scaled`, `norm_blue`, `l2prox*`, `group_prox_early!`) for mathematical or floating-point errors, and state for each whether it is a fair stand-in for the library strategy it is named after.
8. The package's own harness style (benchmark/l2_norms.jl): its probes are closures of the form `() -> PB.prox_block!(out, f, u, k1, γ)` where `PB` is a module passed as a function argument. I measured that this form costs about 23 ns and 64 bytes per call (dynamic global lookup and dispatch) against 5.5 ns for the same call through a captured function value, which compresses tree-to-tree ratios of small kernels toward 1. Verify or refute this from the code (and by experiment if you can run Julia), and say which of that file's probes are materially affected.
