Project rules that the patches must respect: (1) the numerical contract of every public operation must not change on supported inputs — the package documents exceptional behavior carefully (NaN and ±Inf entries, signed zeros, infinite and zero weights and levels, thresholds and sums that overflow or underflow are recomputed in power-of-two units); read docs/src/numerics.md and the docstrings of NormL1, NormL2, GroupNormL2 in src/functions/ for the contract; (2) the maintainer treats any reproducible slowdown above 5% on an existing ordinary hot path as disqualifying, so a patch must not add work to paths it does not speed up; (3) no new numerical-recovery machinery, no duplicated mathematical implementations, simple and maintainable code; (4) Julia 1.10 through current must work (Project.toml compat julia = "1.10").

The patches and what each claims:
- patch-A.diff: `shrink(v, c)` for Base.IEEEFloat becomes `_select_max(v - c, 0) + _select_min(v + c, 0)` with `_select_max(a, b) = ifelse(b > a, b, a)`, `_select_min(a, b) = ifelse(b < a, b, a)`. Claim: same result (===, NaN ≡ NaN) as `max(v - c, 0) + min(v + c, 0)` for every pair (v, c) of IEEE values; other AbstractFloat types keep the old method (BigFloat under directed rounding would differ).
- patch-A2.diff (on top of A): adds `_shrink_nonneg(v, c) = (v - ifelse(m < c, m, c)) + zero(T)` with `m = ifelse(v > -c, v, -c)`, used in the ordinary branch of `_l1_prox_threshold`. Claim: equals `shrink(v, c)` for every v and every c that is not negative (+0, -0, positive, +Inf, NaN); differs for c < 0, which the ordinary branch cannot produce from valid parameters (γλ0 in [floatmin, floatmax] and weights validated nonnegative at construction). A script that checks the claim exhaustively over Float16 is review/st_clampz.jl.
- patch-B.diff: NormL1 `prox!` with a step ARRAY: a specialized `_prox_sep_dense!` method for same-type Float32/Float64 `Array`s that first tests, in one vectorizable pass over the steps (`_steps_normal`, integer min/max of bit patterns), whether every γ[i]·λ0 is in the normal range; if so it runs a branch-free @simd loop that is claimed to compute exactly the ordinary branch of the generic per-entry loop; otherwise it `invoke`s the generic method. Claim: outputs bit-identical to master for all inputs, including in place (y === x).
- patch-C.diff: the unweighted dense NormL1 value sums |x_i| in one @simd loop for strided Float32/Float64 arrays of at most 2^17 entries (`_LS_ONE_LOOP_MAX`, an existing constant used the same way for least squares), Base's pairwise `sum(abs, x)` above. Claim: same value up to summation-order rounding, within the documented error bound; NOT bit-identical.
- patch-C2.diff: `_l2_value` (NormL2 value) and `_square_value` (SqrNormL2 value) call the existing `_sumabs2_loop` instead of `_sumabs2`. Same kind of claim as C.
- patch-D.diff: in `_l2_shrink!`, when the plain sum of squares of a group is exactly zero and the output type is Float32/Float64, the second pass over the group (`_l2_zero_group`) is skipped if `_squares_normal(c * c, length(G), T)` holds for the threshold c; the group is set to +0 directly. Claim: bit-identical outputs and return codes to master for all inputs (the cold path would also return the zero group).
- patch-P155-port-of-PR155-src-only.diff is NOT under review as a patch (it is another contributor's draft); it is included only because it touches the same file as B and C.
