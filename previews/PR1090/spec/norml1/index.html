NormL1 numerical contract

This pilot gathers the existing NormL1 numerical text without changing its wording. The original guide and common-contract anchors remain as forwarding links. Clause conversion and status assignments are a separate review step; prose without an explicit status remains unclassified.

Read How to read the numerical contracts for authority, status meanings and the current migration map.

Identity

Constructors and API help: NormL1. The NormL1 row in the API coverage matrix lists the retained interface.

Source: src/functions/norml1.jl. The evidence section maps the numerical text to retained test files.

Traits

Supported arguments

NormL1 acts on real vector or matrix entries. When weights are given, they must have the same total number of entries as the argument, paired in Julia's linear indexing order. The function also has explicitly supported sparse and symmetric iterate operations; for symmetric matrix storage, matching off-diagonal weights must agree: this is a precondition that the oracles assume and check_symmetric_parameters validates. See Symmetric parameters.

The complete operation and representation boundaries remain in Operations on functions and the NormL1 API entry.

Preconditions

Links only.

Constructor conditions are in the NormL1 API entry. Shared array and precision conditions are in Shapes and destination-first mutation and Supported precision and oracle agreement. For symmetric storage, follow Symmetric parameters.

Results

prox! writes to a supplied destination; value_and_prox! writes the proximal point and returns g evaluated at that stored output. Exact input/output identity is supported, but partially overlapping views are not. Weights are stored by reference, so modifying them also changes the function.

Range clauses

NormL1 values also recover terms λ0*w[i]*abs(x[i]) that round into the subnormal range, which loses accuracy even when the total is normal (#373). Each such rounding loses at most half the smallest subnormal spacing, eps(T)*floatmin(T)/2, so an ordinary sum s ≥ n*floatmin(T) of n terms loses at most eps(T)/2 relative to s and is returned from the unchanged vectorized loop. A smaller sum, a zero one included, is recomputed: the products w[i]*abs(x[i]) are accumulated with their exponents, and λ0 is applied before the single conversion to T. This holds for dense arrays and for the stored entries of SparseIterate, BlockIterate and SymmetricSparseIterate, and for value_and_prox! at its stored output. Zero and infinite levels, infinite weights and NaN/Inf entries keep the rules below. Under an infinite Scaled factor a recovered positive value gives Inf, as the folded level NormL1(Inf, w) does; before #373 a value whose terms all rounded to zero gave NaN there. An exactly zero value still gives 0.

Endpoint clauses

Infinite parameters, NaNs, zeros, overflow and sparse active-zero semantics require extra care. A zero weight leaves an entry unpenalized. An infinite weight sets the proximal output to zero for a finite input value, including at zero level and zero step. For non-finite inputs (NaN, ±Inf) with finite level, there is no fixed-zero guarantee: ordinary soft-threshold arithmetic can return NaN (#853). A genuinely infinite overall level λ0 = Inf separately fixes every positive-weight entry at +0 at any nonnegative step, including non-finite inputs, also at zero step. See the canonical infinite-penalty rule for its interpretation. Zero-weight entries stay free:

prox(NormL1(Inf, [1.0, 0.0, 2.0]), [3.0, 4.0, 5.0], 0.0)  # [0.0, 4.0, 0.0]
prox(NormL1(Inf), [1.0, 2.0], 0.0)                         # [0.0, 0.0]
prox(NormL1(1.0), [1.0, 2.0], 0.0)                         # [1.0, 2.0]: finite level

The infinite overall level and an infinite coordinate weight are distinct: the latter, at a finite level, keeps the finite-input restriction above at every step.

using ProximalBase
@assert NormL1(0.0)([NaN,Inf]) == 0
@assert prox(NormL1(Inf),[NaN,Inf],1.0) == [0,0]
@assert prox(NormL1(Inf),[1.0,2.0],0.0) == [0,0]  # zero step: projection onto {0} (#665)
@assert isequal(prox(NormL1(Inf,[1.0,0.0,2.0]),[3.0,NaN,Inf],0.0), [0,NaN,0])
@assert prox(NormL1(1.0),[1.0,2.0],0.0) == [1,2]  # finite level: zero threshold
@assert prox(NormL1(0.0,[Inf,0.0]),[2.0,3.0]) == [0,3]
@assert isnan(shrink(NaN,1.0))
@assert prox(NormL1(1.0,[Inf]),[2.0],1.0) == [0.0]  # finite input fixed at zero
@assert prox(NormL1(0.0,[Inf]),[2.0],0.0) == [0.0]  # zero level/step
@assert isnan(prox(NormL1(1.0,[Inf]),[Inf],1.0)[1])  # non-finite limitation (#853)
@assert isnan(prox(NormL1(1e300,[1e10]),[Inf],1.0)[1])  # final factor overflows (#866)
@assert isnan(prox(NormL1(1e10,[1.0]),[Inf],1e300)[1]) # intermediate product overflows (#866)
prox(NormL1(Inf),[NaN,Inf],1.0)

Decision on NormL1 non-finite inputs (#853 and #866). A genuinely infinite coordinate weight maps a finite input value to zero, even at zero level and step. For inputs of NaN or ±Inf with finite level, that fixed-zero guarantee is intentionally not extended: retained soft-threshold arithmetic may return NaN. Separately, a threshold made from finite factors can overflow to Inf; with an input of ±Inf, the current result can likewise be NaN even though the mathematical threshold is finite. These examples characterize present behavior, not additional non-finite-output guarantees. A genuinely infinite level at any nonnegative step retains its distinct fixed-zero rule for positive weights, including non-finite inputs; see the zero-step rule.

Failure behavior

Links only.

The common owners are Predictable failures and partial writes, Validation, aliasing and evidence, and NaN, infinities and zeros. Constructor validation is described in the NormL1 API entry.

Limitations and non-guarantees

A threshold formed from entirely finite factors may itself overflow to Inf. For an input of ±Inf this can also return NaN, even though the mathematical threshold is finite. This is a documented, deferred limitation (#866), not an approved change to the proximal kernel. The decision preserves performance of normal Float32/Float64 weighted operations; the measured cost of extra checks is recorded in the numerical endpoint history. See also Array and precision conventions.
