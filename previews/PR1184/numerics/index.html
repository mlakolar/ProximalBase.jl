Numerical contract

This page states the retained numerical behavior and its limits. The historical decisions cover a much larger package; they are historical evidence rather than a live capability list. Current source and tests govern the minimal core.

Supported precision and oracle agreement

The supported CPU numerical targets are homogeneous Float64 and homogeneous Float32. In the supported configuration, the floating-point design/response data, iterate or proximal input point, function parameters (such as levels, weights and centers), proximal step, and floating output buffers all use the same type T. Float64 is the primary performance and accuracy target; Float32 is also tested. Individual methods may accept ordinary integer parameters; this is not a promise to coerce arbitrary mixed floating-point arguments.

Mixed Float32/Float64 is not a guaranteed mode. Some current methods still accept it and perform internal promotion, but their return types, numerical accuracy, exceptional-range behavior and performance are implementation-specific. They are not required to reject such calls. A wider data or parameter type does not establish a general promotion rule for the result. Other real types, including BigFloat, are not guaranteed production types. BigFloat remains useful for independent reference tests.

Conversion can lose the range of a mixed-type parameter. The gradient and point-aware KKT scores of SqrNormL2 convert the level and center entries to their working type. The proximal map also converts the center entries to its working type. The value rounds a Float64 center to Float32 for Float32 data, and a center of BigFloat precision to the data type for Float32 or Float64 data. The same center rounding applies during value recovery. The dense unweighted sum paths of NormL1 and NormL1Nonneg convert the level to the data type. Their entrywise fallbacks use the supplied level when the converted level and entries are finite and the product with the sum is nonfinite. An input that rounds to zero, a subnormal, or infinity can therefore change the result even when the exact result is representable.

For supported homogeneous array-function calls:

  • f(x) returns the value in T = float(eltype(x)).
  • Allocating gradient and proximal operations produce their documented representations in T; SymmetricSparseIterate-specific results are described in the symmetric iterate guide.
  • Mutating operations respect the destination's element type and never change the caller's storage type.
  • value_and_gradient!(out,f,x) returns the standalone value at the input x and stores the corresponding gradient in out.
  • value_and_prox!(out,f,x,γ) returns the value at the stored proximal output, including its rounding, not at an unrounded temporary.
  • Exact input/output proximal identity is supported; built-in gradients reject input/output identity. Other partial/derived-view overlap is unsupported.

Some implementations use promoted private scratch or widened arithmetic to improve numerical stability. Those internals do not widen the supported set of caller precision combinations or imply a generic model-precision override for custom functions.

For Float32 calls, explicitly construct floating parameters and steps in Float32, rather than assuming Julia's Float64 literal 0.5 will be treated as a supported Float32 parameter. The array and precision conventions include a homogeneous example for both supported types.

Overflow and underflow of values

The following range guarantees concern finite-data computations. Non-finite inputs and penalty endpoints have separate rules below.

Range guarantees

Ordinary finite calls use efficient numerical paths. Exceptional paths selectively recover representable values when an intermediate product or sum would overflow or underflow. These include scaled square sums, finite-data affine/quadratic values and products of nonnegative level/step/weight factors. See SqrNormL2 range clauses for its gradient and proximal recovery. SqrNormL2 and LeastSquaresLoss share one squared-residual recomputation: each residual is formed before scaling (as x/2 - y/2, one binade up, when x - y itself overflows) and the squares are summed in units of the largest one. Genuine NaN/Inf data or parameters keep their ordinary IEEE result; only finite inputs whose intermediates leave the range are recomputed. See LinearFunction range clauses for its finite-input recovery. Recovery is worthwhile when it changes a materially inaccurate answer into a representable result in the working precision.

KronQuadratic values and gradients are not among these recovered quadratic values: they use ordinary working-precision arithmetic, in which the selected kernel rounds its operations (a fused multiply-add rounds once), so a result can be subnormal, zero or nonfinite where the exact value is not, depending on the operations. See the KronQuadratic range clauses.

The squared-residual recomputation that SqrNormL2 and the least-squares oracles share has the same kind of boundary uncertainty as the NormL2 recomputation below: within a few eps (the relative error bound of the sum) of the overflow threshold floatmax(T) + ulp/2, where ulp is the spacing between floatmax(T) and its predecessor, it does not decide on which side the exact value lies, so a finite answer there is within the error bound of the exact value and floatmax(T) or Inf can be returned for a value that rounds to the other. This was observed for SqrNormL2, Scaled(LeastSquaresLoss, α)(β) and the oracles of the least-squares section.

See the LeastSquaresLoss range clauses.

The accuracy of a recovered value is an absolute bound B = 4 n eps (sum |terms| + |d|) for n terms. It is a statement about the computed value when the exact value plus B is within the range (|exact| + B <= floatmax). When B exceeds the representable range, there is no guarantee of a finite output. Extreme cancellation among products far beyond the output range (about 2^1077 for Float64, 2^150 for Float32 data) can return an infinity although the exact result is a finite, normal number, in the recovery of a dense argument and in the recovery of the LinearFunction value at a matrix SparseIterate alike (#907). A small d beside a dot that cancels exactly is returned as d when the compensated sum of the products cancels to zero, which is not guaranteed for products of very different sizes.

These are practical numerical safeguards, not a promise of exhaustive range recovery or correctly rounded arbitrary reductions, gradients, or matrix products. When the final mathematical value itself is out of range, an appropriate infinity or underflow to zero may be unavoidable, subject to the function's endpoint semantics. There is no cross-platform or cross-version bitwise arithmetic-order guarantee.

Routes that compute the same proximal point, such as the array prox! and the scalar prox_block, are not guaranteed to agree bit for bit. For homogeneous Float32 or Float64 inputs with γλ between floatmin(T) and 2^125 (Float32) or 2^1021 (Float64), the centered SqrNormL2 proximal point evaluates the coordinates whose argument and center entries have the same sign bit with muladd, which the compiler may or may not contract into one rounding, depending on how it optimizes each call site and on the CPU. On Julia 1.13.4 and an x86-64 CPU with fused multiply-add, with γλ < 1, prox_block was observed to contract it and the vectorized loop of prox! not to, so the two differed in the last place. Both are rounded evaluations of the same formula; the tests compare the two routes within one unit in the last place on selected inputs.

The order in which an ordinary value adds its terms is not part of the contract either. The unweighted NormL1 value of a dense Float32 or Float64 array of 16 to 1024 entries, and the NormL2 value of such an array or strided view, add their terms in one vectorized loop. Julia's sum is also one vectorized loop up to 1024 entries, so the rounding error is of the same kind and grows with the length in the same way, but the result can differ from λ0 * sum(abs, x) or λ * sqrt(sum(abs2, x)) in the last place. The tests bound these values against a high-precision sum and do not compare their bits; shorter and longer arrays use sum.

using ProximalBase
λ = 2.0^-1022
f = SqrNormL2(λ,[-2.0^1023])
x = [2.0^1023]
@assert gradient(f,x) == [4.0]
z = prox(SqrNormL2(2.0^800),[2.0^900],2.0^800)
@assert z == [2.0^-700]
reference = setprecision(BigFloat,256) do
    Float64(big(2.0)^900 / (1 + big(2.0)^1600))
end
@assert z[1] == reference
z

Nested positive finite Scaled factors can retain their exponent sum so an overflowed/underflowed intermediate scale does not discard a recoverable leaf result. This mechanism is implemented for retained kernels, not synthesized for custom functions.

For NormL1 and NormL1Nonneg under Scaled with a positive finite scalar step (Float32 or Float64 factors, step and level), the product αγ of the factors and the step can be below floatmin(T) or above floatmax(T) while the threshold αγλ0wᵢ of an entry is representable, because its weight brings the product back into range. The level that holds the factors and the exponent of the step, which is αγλ0 divided by the significand of γ, is not a normal number when it is zero, when it is subnormal, and when it overflows, which can happen although αγλ0 is at most floatmax(T). In these cases the exponent is split between the level and the step when the step and the level of that split are both normal numbers (the first limit below says when they are not), and the leaf forms the threshold of each entry from them and its weight, so that the weight can bring it back into range. For Scaled(Scaled(NormL1(1.3 * 2.0^20, [2.0^1013]), 2.0^-531), 2.0^-531), the step 2.0^-30 and x = [3 * 2.0^-50], the threshold is 2.2551405187698493e-18 and the scalar step gives [2.662280118581606e-15], as the array step does. The tests compare the proximal point with the point given by the exact threshold, within four units in the last place of the point, on selected inputs and on a seeded sweep over the exponents of the factors, the step, the level and the weight. Two limits, each on its own:

  • When the step or the level of the split is not a normal number, which happens for αγλ0 near or beyond the square of a range limit of the type (floatmin(T)^2, floatmax(T)^2), the exponent is not split and the step is passed rounded (zero, a subnormal number or Inf), as before.
  • ElasticNet keeps the earlier route. Under the same conditions, on either side of the range (αγ below floatmin(T) or above floatmax(T)), also with λ2 = 0, and with a single factor, a scalar step can lose the ℓ₁ threshold where the same step passed as an array of steps gives it. With ElasticNet(1.3 * 2.0^20, 0.0, [2.0^1013]) in place of the NormL1 above, the scalar step gives [2.6623668547554047e-15] and the array step [2.662280118581606e-15].

The dedicated Scaled(ElasticNet(...), α) limitation and its examples are retained in ElasticNet limitations.

NaN, infinities and zeros

There is no universal non-finite endpoint rule or universal step validator. The mathematical prox uses positive finite γ. Many retained closed forms accept zero, negative, infinite or NaN steps and apply their established arithmetic; acceptance does not establish a meaningful proximal minimizer in those cases. Decomposition-based methods are intended for finite data and ordinary valid steps. Do not pass arbitrary non-finite data into them expecting a uniform all-NaN result or a particular exception.

Infinite penalties at zero step

For NormL1(Inf, w), the γ = 0 endpoint is lim_{γ→0+} prox_{γf}(x) with the function f held fixed. That function is the indicator of {0} in each coordinate with w[i] > 0 (an infinite w[i] included) and is zero in each coordinate with w[i] = 0, so the limit is the projection onto the closure of its domain: positive-weight coordinates become exactly +0, even for NaN or ±Inf inputs, and zero-weight coordinates are returned as soft thresholding by a zero threshold returns them (NaN and ±Inf unchanged). Unweighted NormL1(Inf) therefore maps every coordinate to +0. The order of limits matters: for a fixed finite level, shrink(x, γλ) → x as γ → 0+, but NormL1(Inf) is already the constraint at every positive step, so the result is not computed as shrink(x, 0⋅Inf). Among the NormL1 parameters, this rule is specific to the infinite overall level. An infinite coordinate weight at a finite level keeps the narrower #853 rule above (finite inputs fixed; non-finite inputs may give NaN), and finite factors whose product overflows are never treated as an infinite level (the finite-threshold limitation above). For finite levels and finite weights, γ = 0 keeps the identity. A finite positive Scaled factor passes the zero step through, so 2 * NormL1(Inf) projects as well; an infinite factor at a zero step forms the step Inf⋅0 = NaN in the wrapper before NormL1 sees it, and follows the wrapper's existing step arithmetic. ElasticNet follows this rule for an infinite λ1, and implements the same zero-step projection for an infinite ridge level λ2, the indicator of {0} in every coordinate. NormL1Nonneg applies it to an infinite level (positive-weight entries become +0; zero-weight entries are projected onto the orthant, not left unchanged). GroupNormL2 and GroupNormLinf apply the same reading at γ = 0 to an infinite level (groups with a positive weight become +0) and to an infinite group weight, and so does GroupMCP. SparseGroupNormL2 also projects onto its hard domain at zero step. An infinite ℓ₁ level fixes all covered entries, and an infinite ℓ₂ level or weight follows the group rules in the sparse-group endpoint table. NormL0, NormL2 and NormLinf apply it to an infinite level. No other function is claimed to implement a zero-step projection rule.

The endpoint history records the design decisions and performance evidence.

Signed zeros do not activate absent coordinates; explicit active signed zeros can be retained in storage. Symmetric-iterate isequal distinguishes stored negative zero from absent positive zero; == does not. dropzeros! removes either signed zero and preserves NaN/Inf.

Sparse product semantics

The specialized products in the operation table ignore zero iterate coefficients, stored or absent. No term is formed even if the other operand at that coordinate is NaN/Inf. A nonzero NaN/Inf coefficient contributes ordinarily. A zero in a dense factor remains an IEEE zero. A coordinate view uses ordinary dense-vector semantics instead.

using ProximalBase, LinearAlgebra
x = SparseIterate(2)
x[1] = 2
activate!(x,2)
v = [3.0,Inf]
@assert dot(v,x) == 6
@assert isnan(dot(v,coordinates(x)))
dropzeros!(x)
@assert dot(v,x) == 6
dot(v,x)
6.0

The LinearFunction sparse-value rules and example retain the corresponding strong-zero semantics.

Five-argument products with β=0 overwrite the destination without reading its old numerical entries; α=0 scales/clears output without reading right-operand values, after required type/shape/alias checks. Finite summation can depend on activation order; compaction can therefore change final rounding.

The direct A*X*B kernels for matching Float32/Float64 Symmetric-strided factors and matrix iterate X recover the range of individual finite three-factor terms. They promise accuracy within one neighboring floating value for a normal term, or one spacing for a subnormal term, not correct rounding. A non-finite sum is recomputed in scaled units only when all contributing factors are finite; true NaN/Inf data keep ordinary IEEE outcomes. Tiny terms can be rounded away beside large ones. Other mixed/generic product routes do not inherit this specific guarantee.

Validation, aliasing and evidence

Predictable type/shape/parameter errors precede built-in oracle output writes. A read, conversion or numerical failure can leave output changed. Storage state copies and matrix imports have distinct guarantees documented in views and aliasing. Parameter arrays are not made immutable or copied by validation. Call reset_cache! after same-shape cached data changes.
