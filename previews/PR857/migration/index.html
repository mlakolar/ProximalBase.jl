Compatibility and migration

For terms used in the current manual, see the Glossary.

This manual describes the minimal core after merged PR #850, based on 2b373c54. The full post-#848 implementation and its documentation are preserved at eff21b6d7d33c622313122f46c6ee71693c101ee and legacy/full. Those archives are historical references, not a second live API. This development reduction is not a release announcement.

Retained and removed scope

The function library is exhaustive. Group/nonconvex penalties, logistic/Poisson/robust-loss families, constraints and indicators, spectral/nuclear families, generic composition/sum wrappers, LMO, second-order frameworks and GPU extensions were removed. They have no replacement capability implied by this manual. In particular, BlockIterate retains grouped storage, not a built-in group-lasso penalty.

Keep two function objects for f(x)+g(x); no generic function-object sum is retained. Compute mathematical gradient mappings in caller code. Coordinate curvatures and residual/working-set policies are algorithm responsibilities. ProximalSolvers migration is separate; this documentation does not change it.

prox_coordinate!, prox_entry!, cdprox! storage updatesCompute a pure result, then write through public storage; no retained aliases

Treat symmetric owner as AbstractMatrixcoordinates(x) for variables, read-only matrixview(x) for matrix operations
Symmetric-owner x[k]coordinates(x)[k] or matrixview(x)[k], depending on index space
Symmetric-owner broadcast/fillWrite coordinates, or compute a dense symmetric matrix then copyto!
Symmetric array stepsOwner outputs accept scalar steps only; use dense output for entry-step calculations where supported
User separable parameter arrays without metadataDeclare ProximalBase.entry_parameters and validate pair symmetry

The working set survives value writes. fill!(x,0) followed by dropzeros!(x) clears array iterates; use fill!(coordinates(x),0) for a symmetric owner. Same-kind matching state copies replace active state; ordinary broadcasts copy values and keep previous activity. Read the storage guide before assuming conventional dense-array behavior.

Historical contracts

Current developer contracts are reconciled against retained methods and tests. Historical acceptance records remain available at the immutable archive, including pending requirements and measured experiments. They are not automatically current guarantees. Numerical endpoints, aliasing and decomposition caches must follow the retained numerical contract.
