Operations on functions

Assumes: gradients and basic Julia · You will learn: the complete function-operation catalog, including proximal maps, mutation and coordinate checks.

ProximalBase provides operations on mathematical functions. They answer questions such as “What is the objective value?”, “What is its gradient?”, or “What is the proximal point?” An optimization algorithm combines these operations to update its variables and check optimality.

Available operations at a glance

This is the complete set of exported function operations in the current package, grouped by purpose. Most operations are supported by specific function families, not every function object. The table is a starting point; each operation is explained below, including its mathematics and Julia usage.

f(x) is ordinary callable-function syntax rather than a separately exported named operation. There is no allocating value_and_prox method. The scalar utility shrink(v,c) returns $\operatorname{sign}(v)\max(|v|-c,0)$ for nonnegative threshold $c$; see The ℓ₁ norm.

Scalar observation losses have their own interface: ProximalBase.ScalarLoss provides ProximalBase.deriv, ProximalBase.deriv2, ProximalBase.curvature, and ProximalBase.value_and_deriv for an individual prediction and observation. These are distinct from array gradients and proximal operations. See Scalar losses: interface and operations and the scalar-loss API reference. Validation hooks used when defining new functions are described under Writing your own function. Storage operations on SparseIterate, BlockIterate and SymmetricSparseIterate are cataloged in the Iterates guide.

Mathematical setting

Many optimization problems combine a smooth loss and a penalty:

\[\min_x\;F(x)=f(x)+g(x).\]

The algorithm can evaluate f and g, differentiate f, and apply a proximal operator to g. The available operations depend on the function's traits and concrete methods.

Evaluating a function

Question: What is the value of a function at the current point?

For example, the squared Euclidean norm with scale one is

\[f(x)=\frac12\sum_{i=1}^p x_i^2=\frac12\|x\|_2^2.\]

using ProximalBase
x = [2.0, -1.0]
f = SqrNormL2(1.0)
f(x)                         # 2.5
2.5

The result of f(x) is a scalar. To evaluate a composite objective, add the values of its constituent functions:

g = NormL1(0.5)
f(x) + g(x)                  # 4.0
4.0

Values are useful for comparing candidate solutions and monitoring progress.

Computing a gradient

Question: In which direction does a differentiable function increase most rapidly near the current point?

The gradient of $f:\mathbb R^p\to\mathbb R$ collects its partial derivatives:

\[\nabla f(x)=\begin{bmatrix} \partial f(x)/\partial x_1\\ \vdots\\ \partial f(x)/\partial x_p \end{bmatrix}.\]

For $f(x)=\|x\|_2^2/2$, the gradient is $\nabla f(x)=x$. Moving a short distance in the negative-gradient direction gives a gradient-descent step:

\[x^+=x-\gamma\nabla f(x),\qquad\gamma>0.\]

grad = gradient(f, x)        # [2.0, -1.0]
trial = x - 0.1 * grad       # [1.8, -0.9]
2-element Vector{Float64}:
  1.8
 -0.9

gradient(f,x) returns a new gradient array. gradient!(out,f,x) computes the same gradient in an existing destination. The destination goes first:

out = similar(x)
gradient!(out, f, x)
@assert out == grad

Use the in-place form when an algorithm repeatedly needs a gradient and can reuse its buffer. Not every function has a gradient: for example, $\|x\|_1$ is nondifferentiable at zero.

Evaluating a value and gradient together

Question: Can we obtain both the objective value and gradient at the same point without making two separate oracle calls?

value_and_gradient(f,x) returns the pair $(f(x),\nabla f(x))$. The mutating form writes the gradient to out and returns the value at the input x:

value, grad2 = value_and_gradient(f, x)
buf = similar(x)
value2 = value_and_gradient!(buf, f, x)
@assert value == value2 == f(x)
@assert grad2 == buf == gradient(f, x)

This fused operation is convenient in methods that evaluate both the objective and a descent direction at every iteration. It does not necessarily promise fewer allocations or a particular speedup.

Computing a proximal point

Question: What point balances decreasing a penalty with staying close to the current trial point?

For a function $g$ and a positive step $\gamma$, the proximal operator solves

\[\operatorname{prox}_{\gamma g}(v) =\operatorname*{argmin}_z\left\{g(z)+\frac{1}{2\gamma}\|z-v\|_2^2\right\}.\]

Unlike a gradient step, a proximal map can handle nonsmooth penalties. For $g(x)=\lambda\|x\|_1$, it is soft thresholding:

\[[\operatorname{prox}_{\gamma g}(v)]_i =\operatorname{sign}(v_i)\max(|v_i|-\gamma\lambda,0).\]

prox(g, x, 1.0)              # [1.5, -0.5]
2-element Vector{Float64}:
  1.5
 -0.5

prox!(out,g,x,γ) writes the proximal point into out and returns that destination. value_and_prox!(out,g,x,γ) writes the point but instead returns the value of g at the computed output:

point = similar(x)
prox!(point, g, x, 1.0)
@assert point == [1.5, -0.5]
penalty_at_point = value_and_prox!(point, g, x, 1.0)
@assert penalty_at_point == g(point)

The distinction matters: value_and_gradient! returns the value at the input, whereas value_and_prox! returns the value at the stored proximal result.

Putting gradients and proximal maps together

When minimizing $f+g$ with a smooth $f$ and a proximable $g$, a proximal-gradient step first moves using the gradient of $f$ and then applies the proximal map of $g$:

\[x^+=\operatorname{prox}_{\gamma g}\bigl(x-\gamma\nabla f(x)\bigr).\]

γ = 0.1
x_next = prox(g, x - γ * gradient(f, x), γ)
@assert x_next == [1.75, -0.85]
x_next
2-element Vector{Float64}:
  1.75
 -0.85

This is one step, not a complete solver. A solver chooses suitable steps, repeats the update and checks convergence. See proximal-gradient methods for that context.

Operating on individual coordinates or blocks

Question: Can the algorithm update only one coordinate or small block instead of processing the whole vector?

If $g(x)=\sum_i g_i(x_i)$ is separable, its proximal operator can act independently on scalar coordinates. The scalar hook prox_block(g,v,i,γ) returns

\[\operatorname{prox}_{\gamma g_i}(v) =\operatorname*{argmin}_z\left\{g_i(z)+\frac{(z-v)^2}{2\gamma}\right\}.\]

Here v is the proposed scalar point and i identifies the global entry, so coordinate-dependent parameters can be selected.

prox_block(g, 2.0, 1, 1.0)  # 1.5
1.5

value_entry(g,v,i) evaluates the scalar contribution $g_i(v)$ where this operation is implemented (not for every mathematically separable function). A custom group function can instead implement prox_block!(out,g,u,k,γ) on compact vector buffers. These hooks compute mathematical answers; they do not update an iterate's active set or write back to solver state. See Coordinate oracles and Writing your own function for precise contracts.

Checking optimality with KKT conditions

This uses the nonsmooth KKT conditions, not just stationarity equations involving ordinary derivatives.

Question: Is a coordinate that we have kept at zero allowed to remain zero at the optimum?

For a convex differentiable loss $f$ and an $\ell_1$ penalty $g(x)=\lambda\|x\|_1$, the optimality condition for a zero coordinate $i$ is

\[|\nabla_i f(x)|\leq\lambda.\]

The scalar kkt_violation(g,grad,i) measures $|\mathrm{grad}_i|-\lambda$ for NormL1 (with its appropriate coordinate weight). A positive result signals that the zero-coordinate condition is violated:

gradient_at_zero = [0.8, 0.2]
(kkt_violation(g, gradient_at_zero, 1),
 kkt_violation(g, gradient_at_zero, 2))
(0.30000000000000004, -0.3)

For this penalty with $\lambda=0.5$, the result is $(0.3,-0.3)$: the first zero coordinate fails the test; the second passes it. This is not a general optimality certificate for a nonzero coordinate or the entire vector. The iterate-aware variant kkt_violation(g,grad,x,k) interprets k in the iterate's coordinate or block space. See Coordinate descent.

Restricting a function to selected coordinates

restrict(f, S) constructs a smaller function on selected coordinates. It does not require separability: quadratics and vector-response least squares are supported alongside separable functions. Coordinates outside S are normally fixed at zero, rather than their current iterate values; centered squared norms additionally omit a constant from the excluded coordinates.

See Restricting functions for the precise mathematics, nonseparable examples, supported methods, and the distinction between zero-fixed and nonzero-fixed subproblems.

Gradient bounds and step sizes

Question: How large a gradient step can the algorithm safely try?

A differentiable function has an $L$-Lipschitz gradient if

\[\|\nabla f(x)-\nabla f(y)\|_2\leq L\|x-y\|_2.\]

Such a bound helps guide step sizes: for many convex smooth objectives, a step no larger than $1/L$ is a standard starting choice. lipschitz(f) returns a bound for supported smooth function families.

L = lipschitz(f)
@assert L == 1.0

For a real matrix $X$, the squared spectral norm is $\|X\|_2^2=\lambda_{\max}(X^\mathsf{T}X)$. opnorm2(X) returns an iterative estimate of this quantity:

using ProximalBase
Xnorm = [3.0 0.0; 0.0 4.0]
estimate = opnorm2(Xnorm)
# The exact squared spectral norm is 4² = 16.
(estimate = estimate, exact = 16.0)
(estimate = 16.0, exact = 16.0)

An estimate is not a certified upper bound. Do not rely on it alone for step-size safety; use an independently valid bound or backtracking.

Invalidating cached calculations

Question: What if I modify data already stored by reference inside a function object?

Some function objects reuse matrix decompositions to speed up repeated proximal evaluations. If the data change but their shape stays the same, reset_cache!(f) invalidates any such cached decomposition so a later computation can rebuild it. This is a lifecycle operation, not a new mathematical function.

For least squares, the proximal point at $v$ solves $\min_z\{\|y-Xz\|_2^2/2+\|z-v\|_2^2/(2\gamma)\}$. If $X$ changes, the cached matrix decomposition no longer describes the current problem.

using ProximalBase
Xcache = [1.0 0.0; 0.0 1.0]
ycache = zeros(2)
loss = LeastSquaresLoss(ycache, Xcache)
v = ones(2)
_ = prox(loss, v, 1.0)   # may build and cache a decomposition
Xcache[1, 1] = 2.0       # same dimensions; different mathematical loss
reset_cache!(loss)
z = prox(loss, v, 1.0)
@assert z ≈ [1 / 5, 1 / 2]
z
2-element Vector{Float64}:
 0.2
 0.5

Changing data dimensions requires constructing a new function. See Array and precision conventions for ownership details.

Calling conventions, results and supported inputs

The mathematical definitions above are the same for allocating and mutating calls. In Julia, the ! suffix indicates mutation, not a guarantee that the implementation performs no allocations.

Mathematical operationAllocating callMutating callMutating return
Gradientgradient(f,x)gradient!(out,f,x)out
Value and gradientvalue_and_gradient(f,x)value_and_gradient!(out,f,x)Value at input x
Proximal pointprox(g,x,γ)prox!(out,g,x,γ)out
Value and proximal pointnonevalue_and_prox!(out,g,x,γ)Value at the stored proximal point

Mutating calls put the destination first. For ordinary arrays, gradient(f,x) allocates a dense gradient and prox(f,x,γ) allocates a floating-point result compatible with the supported input type. Some specialized symmetric-storage calls have different result types; see the symmetric iterate guide.

In-place calls and overlapping memory

Built-in gradient operations require a destination separate from their input: gradient!(x,f,x) is not supported. Proximal maps support the exact same object for input and output, as in prox!(x,g,x,γ). Other partially overlapping views are not supported and may produce incorrect results without warning. Use an independent input copy when in doubt. Parameter and scratch ownership details are in Numerical usage.

Different steps for different entries

For separable penalties, some proximal methods accept a vector or array of positive steps γ, one for each input entry. The mathematical problem then becomes

\[\operatorname*{argmin}_z\left\{ g(z)+\sum_i\frac{(z_i-x_i)^2}{2\gamma_i} \right\}.\]

using ProximalBase
x_steps = [2.0, -1.0]
steps = [0.5, 2.0]
z_steps = prox(NormL1(0.5), x_steps, steps)
@assert z_steps == [1.75, 0.0]
z_steps
2-element Vector{Float64}:
 1.75
 0.0

An array of steps is not universally supported. Generic SeparableFunction array proximal operations and ZeroFunction support it; Scaled forwards it only when the wrapped function does. Do not assume the same for SqrNormL2, LinearFunction, LeastSquaresLoss, or QuadraticFunction. A SymmetricSparseIterate output accepts scalar steps only.

Shapes, errors and precision

Each concrete function defines which vector, matrix and storage inputs it supports; a true trait does not guarantee every argument shape. Built-in methods check predictable shape, type and parameter errors before output writes, but an error during computation may leave a partially changed destination. Positive finite steps are the standard mathematical setting. Exceptional NaN, infinite and zero steps are function-specific rather than universally validated. See Numerical usage, Numerical contract, and the API reference for precise limits.

Symmetric matrices and coordinate updates

Proximal operators on symmetric iterates use the Frobenius geometry of the full represented matrix. Off-diagonal independent coordinates appear twice in the matrix norm. Supported functions have explicit methods for this storage type; not every gradient or proximal operation accepts it. See SymmetricSparseIterate and Symmetric parameters.

Scalar prox_block works on a supplied trial value, not an iterate: the caller must separately write the returned result to the appropriate entry or block and update its own solver state. For precise indexing and ownership rules, see Coordinate oracles.
