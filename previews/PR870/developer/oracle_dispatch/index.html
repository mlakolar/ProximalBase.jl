Function traits, dispatch and coordinate oracles

Capability declarations and method dispatch

The first four traits default false on AbstractFunction types, with instance forwarding. iszeropreserving defaults false on instances. SeparableFunction sets separability/proximability true and supplies generic values/prox from two scalar hooks. It does not supply gradients, KKT, restrict or bounds.

Traits inform algorithms; concrete Julia methods implement calls. A retained SqrNormL2 has isseparable=true and scalar prox_block but no value_entry or array-step prox. A custom block-only hook has an allocating wrapper but no full-array prox. Owner methods are explicit, since the owner is not an array. Avoid broad method declarations that make applicability appear wider than the implementation's actual supported domain.

Generic defaults and public boundaries

The general gradient! fallback checks output/input, calls the fused gradient and returns out. Implement value_and_gradient! if relying on it. Allocating variants allocate a dense gradient. The default fused prox computes prox! then the value at out; its scalar return is not a (value,out) tuple. There is no allocating valueandprox binding.

Custom public overrides replace the checked boundary. Validate real types, shape, parameters and aliases yourself and invoke check_symmetric_parameters if accepting an owner. Generic check_parameters defaults to nothing; for a parameterized extension implement it. For custom SeparableFunction, entry_parameters must be declared for owner use. Built-ins have private checked/ unchecked routes to avoid repeated full scans; those private helpers are not extension targets. Generic custom dispatch calls public methods rather than requiring an _isbuiltin escape.

Array steps are a distinct method family: generic separable and zero functions accept entry steps; Scaled forwards when its leaf supports them. Owner array steps are rejected before writes. No trait automatically supplies this dispatch.

Pure hooks and storage kernels

Raw scalar value_entry/prox_block use global entry indices. Generic sparse kernels pass stored coordinate IDs for SparseIterate, global members for blocks, and converted full matrix indices for owner variables. Symmetric values count both mirrored entry terms. A declared zero-preserving function can skip inactive zeros; custom metadata still receives conservative full pair validation.

Compact-vector prox_block! is a public extension hook with no retained built-in implementation. The default allocating method supplies an independent floating Vector and delegates. Its index denotes a custom block and its vectors follow that block's order. The hook author validates buffer shapes/types/overlap; no generic full-array lifting, wrapper forwarding or KKT follows from it.

The solver constructs trials, verifies group layouts, calls the mathematical hook in independent scratch, writes public storage, then updates residuals and its own caches. Neither scalar nor vector hook silently activates a coordinate. For symmetric scalar updates it validates parameters first and converts the independent ID to the full-entry index; no owner is available in the raw hook.

KKT and restrictions

Retained scalar screens are explicitly implemented for NormL1, SqrNormL2, ZeroFunction and LinearFunction; Scaled forwards. Four-argument dispatch adds coordinate semantics and checks, or maximum-over-group for BlockIterate. It does not turn a quadratic/least-squares loss into a scalar penalty screen. KKT means a signed screen at a coordinate assumed zero, not a general solver residual. restrict slices supported parameters; no default exists for custom functions. A restricted quadratic keeps its constant and assumes omitted variables zero; vector-response least squares keeps Y and selects columns.

See the extension tutorial, symmetric parameters and current pure block contract.
